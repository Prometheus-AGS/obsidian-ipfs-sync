# Spec 007 — Automated Karpathy Logs (Knowledge Format) for Learning + Agentic Support

Status: **spec for later reference — no phases started.**
Grounded in: `karpathy-progress-memory` skill + `references/record-schema.md`
(the current "new knowledge format", verified on disk 2026-09-29).

## Intent

Karpathy-style progress records — compact, evidence-backed, failure-honest —
should be captured **automatically at runtime** (not just by dev harnesses at
task boundaries), in the latest knowledge format, and fed back into the system
for **learning** (human and model) and **agentic support** (agents that read
the decision path before acting).

## The format (authoritative, from record-schema.md)

Each record is a Prometheus **`Reference` page**:

- Stable slug, UTC timestamps, revision, phase/status tags.
- Six sections: **Intent → Observed state → Decision and delta → Verification
  → Failure/lesson → Next experiment.**
- Facts only with evidence; inferences and rejected alternatives separated.
- Secrets redacted; machine-specific roots replaced with `$REPO_ROOT`.
- Divergent history is never overwritten — new revisions/provenance variants.

Storage lanes (existing Prometheus convention):

| Lane | Path | Synced? |
|---|---|---|
| Project wiki | `.prometheus/knowledge/wiki` (repo) | git |
| Private superset | `~/.prometheus/knowledge/private/<project-slug>/wiki` | **never** — local only |
| Shared KB | `~/.prometheus/knowledge/shared` | curated, reviewed lessons only |

Tooling already exists: `scripts/record-progress.mjs` (recorder),
`prometheus learn --capture-session --compile --lint` + `pk lint` (phase-gate
pipeline), `prometheus learning status --json` (queue/dead-letter telemetry).

## What "automated" adds beyond the dev-harness behavior

The skill today fires from KBD/harness task boundaries. This spec extends
capture to **runtime events**, emitted by the plugin / UAR-lite / Node scripts:

| Event | Captured automatically |
|---|---|
| Publish/pull completes | intent (what changed), delta (root CIDs, file counts), verification (resolve + hash-match evidence), failures (proxy quirks, conflicts) |
| Conflict occurs | record with both contents' hashes, resolution taken, lesson |
| Agent run ends (UAR-lite/UAR) | the run becomes a Reference page; agent's own failure/lesson section is mandatory |
| Verification discovery | "compiled but didn't run" class of findings (per skill's prohibition) |
| Phase gates (dev) | existing full pipeline — unchanged |

Design properties:

1. **Emit raw anywhere, compile centrally.** Phones emit records (vault notes
   or `kv_*` queue); compile/lint runs where `prometheus` CLI exists
   (desktop/CI). Mobile never needs the toolchain.
2. **Two vault integration modes (decision pending, see Q1):**
   - **Local-only mode:** runtime records land under `~/.prometheus/...`
     (private superset) and never touch IPFS.
   - **Synced mode:** a curated subset (slug, six sections, no local paths)
     lives in a vault folder (e.g. `.ipfs-sync/learning/`) and syncs like any
     note — every device and agent sees the decision path.
3. **Agentic support:** agents get a tool/skill to (a) **append** records
   (their own runs, with honest failure sections) and (b) **query** the record
   corpus via the spec 006 stores — graph edges link records to the notes they
   concern (`provenance: 'agent:*'`), vector search finds past lessons by
   semantic similarity. An agent that can read *why* a decision was made stops
   re-litigating it.
4. **Redaction is load-bearing** (skill prohibition, applies to automation):
   no keys/tokens; `$REPO_ROOT` substitution; private superset never published
   — automation must not widen the blast radius of a redaction failure, so the
   synced subset is generated by an allowlist transform, not by copying.
5. **Never overwrite history** — automated re-runs produce revisions, and the
   compile step preserves imported historical variants (per skill).

## Relationship to the learning loop

Records are the raw material for the Feynman-style loop in the ecosystem
(learn-survey → feynman-loop → learn-grade → learn-retain): graded explanations
of *this project's* records become durable knowledge; `learn-retain` schedules
re-review so lessons actually stick. Agents benefit symmetrically: the shared
KB is their curriculum, the project wiki is their runbook.

## Open questions

1. **Synced vs local-only records** — do learning logs leave the device?
   Leans on the deferred Phase 2 encryption decision (spec 005 §open questions):
   synced subset is acceptable only with encryption or strict curation. Default
   proposal: local-only until encryption lands.
2. **Record volume budget** — sync runs can be frequent; need a compaction
   policy (per-day rollup of routine publish/pull; full records only for
   anomalies/conflicts/phase gates)?
3. **Slug/namespace for runtime records** — separate phase tag (`runtime/…`)
   from KBD dev records so compile/lint can apply different strictness?
4. **Vault folder name** for the synced subset — `.ipfs-sync/learning/`?
   (Dot-folder keeps it out of graph/backlink noise.)
5. Do agent-appended records require a verification section, or is an explicit
   "unverified" status tag enough for agent-generated claims?
