History pruning policy

History pruning policy

tagsipfs-sync, decisionupdated2026-09-30

Every publish adds one encrypted manifest copy under manifests/. On a daily auto-publish the folder grows by roughly one file per edit session, so a vault that is never pruned will eventually hit the publisher's file limit on the node.

Decision

Keep the newest 200 history entries by default. prune-history removes the oldest first and never touches current/. The plugin does not prune; only the CLI does, because pruning is irreversible and the removal guard counts deletions in current/ only, not history files.

Open

  • Should a pruned entry's root CID stay pinned until GC? See [[IPFS pinning and GC policy]].
  • Does the restore list need to say that older entries were pruned?

Why does pull refuse a plaintext root?

Vault agent local

The release retro says 0.2.0 wrote plaintext. The format notes record that version 1 roots are refused on read because the reader was removed. The question is about the refusal, so the format note is primary.

Arguments
{ "query": "plaintext root refused", "scope": "vault", "k": 5 }

Result · 3 notes above 0.62 similarity

Because the reader that understood a version 1 (plaintext) root was removed when encryption landed1. Release 0.2.0 is the only build that ever published plaintext, and anything it published is readable by anyone with the CID2. Refusing to read it is how the current tree avoids being used to pull an unencrypted vault into a device that then publishes it encrypted, hiding the earlier exposure.
