## Goals / Non-Goals

**Goals**
- A second device unlocks and restores a vault byte for byte, every mvp-06 reader requirement applied, nothing partial written on failure.
- A pull never leaves the device able to publish a manifest that silently drops files it could not restore.
- Sequence enforcement that states what it does not prevent, with a recovery for forks and a deliberate restore that cannot lower a record.
- Two devices can take turns, and the failure of overlapping publishes is detected and recoverable without deleting `.ipfs-sync/`.
- Path handling that does not rely on an enumerated list of aliases.
- The plugin's memory and disk behaviour is bounded by named constants, or it refuses.

**Non-goals (07b):** key management (rewrap, cost increase, accept changed slots), `prune-history`, the mass-removal guard, removal of the v1 reader, removal of the guard, phone timing, the operator run, Release 2. **Non-goals (later):** revocation or VCK rotation, multi-writer manifest merge, device pairing (SPAKE2, UCAN), padding, hiding metadata, mobile verification.

### 2. RootState version 3
`ROOT_STATE_VERSION` becomes 3. The decoder accepts 2 and 3 and always returns a v3 shape. Version 3 states are refused by older builds with their existing "format N is not supported" error, which is the fail-closed outcome for a downgrade (an old build that ignored the new fields could publish a manifest that drops files). Consequence: an operator who runs an mvp-06 dev build after this change must abandon or re-pull; accepted because no released build wrote a v2 encrypted state.

| Field | Meaning |
|---|---|
| `sequence`, `manifest` | the authenticated node manifest header this baseline came from (`sequence === manifest.sequence` stays enforced). `manifest.files` is the baseline per path: for a path restored on the last pull or written by this device's own publish it is the node's entry; for a path this device could not restore (see `unmaterialized`) it is the node's entry too, so that publish can copy it; a path that is excluded or has an unsafe shape is absent. |
| `unmaterialized` | sorted list of unique paths whose `manifest.files` entry is the node's and whose content this device does not hold at that version: `unfetched`, `integrity-failed`, and `policy-skipped` with class `platform`. Bounded by the manifest entry cap. Publish copies these entries unchanged and never diffs them against local files (decision 7). Empty for a state written by publish on a device with nothing carried. |
| `manifestIdentity` | lowercase hex sha256 of `serializeManifestV2(nodeManifest)` (`encrypted-manifest.ts`), the canonical plaintext serialisation of the authenticated node manifest this baseline came from. It is stored, not recomputed from `manifest`, because the stored `manifest.files` is merged (it lacks excluded and unsafe-shape paths). For a v2 state it is computed from `manifest` at upgrade, which is exact because a v2 state always holds an unmerged manifest. |
| `previousIdentity` | lowercase hex sha256 or `null`: the `manifestIdentity` this device's state held when it built the manifest it last published (the manifest it built on); `null` for a first publish, after a pull, and for a state upgraded from v2. Read only by fork resolution (decision 9). |
| `highestSequence`, `highestIdentity` | the highest authenticated manifest this directory has accepted, by sequence, and its identity. Never lowered by a restore. Equal to `sequence` and `manifestIdentity` except after a restore or a first pull that used an older explicit target under a floor. |
| `complete` | boolean, informational. False when the last (non-restore) pull had an `integrity-failed` or `unfetched` file. It is shown in the UI and sets the exit code; publish does not refuse on it (decision 7). A later pull that restores every non-skipped file sets it true. |
| `devicesSeen` | manifest `device` values seen on authenticated manifests (pulled or published), own label included, unique, in first-seen order, at most 16; when full, the earliest-seen value is dropped (a full list still counts as "another device known" when any value differs from this installation's). |
| `restoredFrom` | optional: the lowest sequence a deliberate restore accepted since the last normal pull. Informational and shown in the UI. |
| `encryptedSeen` | still written while 07b has not removed the latch consult; decoder does not require it for v3. |

**Strict v3 decoding (Q-08).** The v3 decoder requires every new field with no defaulting: `complete` is a JSON boolean, `manifestIdentity` and `highestIdentity` are 64 lowercase hex, `previousIdentity` is 64 lowercase hex or `null`, `highestSequence` is a safe integer not below `sequence`, `unmaterialized` is a sorted array of unique strings each present in `manifest.files`, `devicesSeen` is an array of at most 16 unique strings; when `highestSequence === sequence`, `highestIdentity` must equal `manifestIdentity`. A v3 file that lacks a field is a `RootStateError`. Only format 2 gets the upgrade defaults (`complete: true`, `unmaterialized: []`, `previousIdentity: null`, `highest*` from `sequence`).

Ciphertext hashes are not used for equality. `manifest.enc` uses a random nonce, so a resume or a repair that re-encrypts the same plaintext manifest at the same sequence produces different bytes and would be a false fork forever. Equality is `manifestIdentity`. Note the identity includes `publishedAt` and `device`: two manifests at one sequence with the same files but different `publishedAt` are different manifests, which is correct for a fork (two publishers) and does not arise from resume, which re-encrypts the journal's pending manifest unchanged.

**Writers (C-07).** All four writers produce v3 states. `finishPublish` (`publish-commit.ts`) writes `manifestIdentity` of the manifest it wrote, `previousIdentity` (the identity of the baseline it built on), `highest*` raised to it, `complete: true`, `unmaterialized` from the plan's carried paths, and `devicesSeen` plus its own label. `adopt` (`publish-resume.ts`) writes the same fields from the journal's pending manifest; it raises the directory's `highest*` to the pending manifest (the state already claims that sequence, and the invariant `highestSequence >= sequence` must hold) and does not write the floor: the floor is raised only by `finishPublish` and by a pull. A pull that finds the node at a lower sequence than such an adopted state refuses with the text "an unfinished publish of sequence N is pending; run publish" instead of calling it a rollback. `finishUnchanged` (`publish.ts`) spreads the existing state and changes only `mtimes`. A pull writes the fields in decision 6 step 8.

### 3. Device-local store, device id, sequence floor
A small port `DeviceStore { get(name): Promise<Bytes|undefined>; set(name, bytes): Promise<void> }` for data that must live outside the vault-synced folder.
- CLI: a per-user state directory (`$XDG_STATE_HOME/ipfs-sync`, else `~/.local/state/ipfs-sync`; macOS `~/Library/Application Support/ipfs-sync`; Windows `%LOCALAPPDATA%\ipfs-sync`), created 0700, files 0600, owner checked on read, symlinks refused. 07b's checker and recorder compute the same directory; a test in 07b pins the two computations equal (07b design 9).
- Plugin: a `deviceStore` section of the plugin's `data.json` (settings model gains it; `data.json` sits under `.obsidian/plugins/ipfs-sync/`, which is excluded from publish and refused by pull). If the user syncs `.obsidian/plugins/` by another tool the device id is copied to another device; documented residual.
- **Device id**: 16 random bytes, hex, generated once per installation. The manifest `device` becomes `<label>-<first 12 hex of the id>` where `<label>` is the sanitised `IPFS_SYNC_DEVICE` (default `cli`, or `obsidian` for the plugin) cut to 40 code points; total at most 64. `PLUGIN_DEVICE` and `DEFAULT_DEVICE` remain only as labels. The id reaches `manifestFrame` through `PublishDeps` (an optional `deviceId` provider) rather than a second environment variable.
- **Sequence floor** `sequence-floor.json` in the DeviceStore: `{ version: 1, floors: { "<vaultId>": { sequence, identity, at } } }`, at most 64 vaults (oldest by `at` dropped). Keyed by `vaultId`, not by directory or `mfsRoot`, so `abandon`, deleting `.ipfs-sync/` and changing `mfsRoot` do not reset it. A first pull into a directory with no state uses the floor as the record.
- **Writes are read-merge-max (Q-05).** Every floor write re-reads the stored file, takes the higher sequence per `vaultId` (at equal sequence keeps the stored identity unless the write is a fork resolution), and writes the result; the CLI store writes through a temporary file and rename. In the plugin the floor lives in the `deviceStore` section of the settings and `settings-store.ts` stays the single writer of `data.json`: its `update` applies the same per-vault maximum to `deviceStore` on every save, so a change function built from a stale snapshot cannot lower a floor. Residual: two CLI processes on different vaults can lose one another's update to the shared file; the loss only removes protection for a directory whose own state has been deleted.
- **Effective record** = the higher `highestSequence` of the directory's state and the floor for that vault. At an equal sequence the two identities must match, otherwise the verdict is `fork`. Writes: floor first, then state, so a crash leaves floor ahead, which is the safe direction.
- What the floor does not do: it cannot stop a user who deletes the per-user store or reinstalls; it is one more local file. A key holder can publish sequence 2^53-1 and every device that pulls it records it (Q-12); **the documented recovery** is to delete the floor file in the per-user store (CLI: `sequence-floor.json`; plugin: the `deviceStore` section of the plugin data) and the state file of each affected directory, then pull again, which is a first pull with its confirmation. `abandon` still moves state, journal and slot copy and now prints the floor it keeps (task 1.5).

### 4. Pull verdicts (pure function `pull-sequence.ts`)
Input: effective record (or none), candidate = authenticated manifest `{vaultId, sequence, identity}`, target kind (`name`, `root-cid`, `manifest`), flags (`allowRollback`, `resolveFork`, `expectMinSequence`, `expectVaultId`). Output, in this order:

| # | Condition | Verdict |
|---|---|---|
| 1 | `expectVaultId` set and differs, or `expectMinSequence` set and candidate is lower | `expectation-failed` (not overridable) |
| 2 | no record | `first-pull` (confirmation required, see 5) |
| 3 | `vaultId` differs from the record's | `other-vault` (not overridable) |
| 4 | sequence lower than `highestSequence` | `older`; becomes `restore` only if target kind is `root-cid` or `manifest` and `allowRollback` is set; a name-resolved lower sequence is refused and the message does not mention the flag |
| 5 | equal sequence, identity differs | `fork`; becomes `fork-resolution` only if the target is `name` and `resolveFork` is set; `allowRollback` has no effect |
| 6 | equal sequence, identity equal | `same` (proceed: re-pull, retry of an incomplete pull) |
| 7 | higher | `newer` (proceed; raise the record) |

`vaultId` is readable from the parsed key-slot file before any derivation, so `expect-vault-id` and the other-vault check against the floor are applied before Argon2id runs.

### 5. Targets, flags, first pull
- Targets: the IPNS name (`--name`, or the owned publication key), `--root-cid <cid>`, `--manifest <cid>` (reads the history entry for that tree CID under the resolved root, either naming form), plugin pull-name `/ipfs/<cid>` (equivalent to `--root-cid`; task 5.0 makes the settings parser accept it). All targets pass unlock, authentication, verdicts and verification.
- `--allow-rollback` exists only for explicit targets and, in the plugin, only from the Restore action, never from the plain Pull command.
- `--expect-min-sequence <n>` and `--expect-vault-id <32 hex>` apply to every pull.
- **First pull confirmation.** After the manifest authenticates and before any file write or floor write, a first pull shows the sequence, `publishedAt` and `device` (all authenticated, all chosen by a vault-key holder) and asks for a yes. CLI: interactive prompt, or `--accept-first-pull` for a non-interactive run; a non-interactive run without the flag refuses. Plugin: a dialog. Declining writes nothing, including no floor entry.
- **Trust statement.** `--root-cid` and `/ipfs/<cid>` select what the gateway serves for that CID; the gateway path does not verify returned bytes against the CID on the client. So an explicit CID narrows the question to the gateway's honesty and to authenticated content; it does not bind the bytes. Authenticated content is what the vault key signs: a hostile gateway can serve an old genuine manifest or withhold, not forge.

### 6. Pull flow
1. Guard (still present): the existing destination guard and the marker rule of decision 16 run first, before any request. The state-folder symlink check runs with it. (07b 3.2 moves that check into `state-folder-guard.ts` and calls it from this step.)
2. Take `publish.lock` (CLI: `createNodeLockFile`; plugin: the adapter lock file the publish runner uses) and the in-process lock. A held lock is a refusal with the same text as publish. Sweep `.ipfs-sync/tmp/` (stale `.part` files) while holding it.
3. Resolve the target (nocache for names). Read-only reads of `keyslots.json` and `manifest.enc` through the gateway, each after `files/stat`-style size checks where the target is a name-resolved MFS path, and with the mvp-06 caps.
4. Key slots: parse canonically; with a local copy, unlock it first (no network for a wrong passphrase) and compare the node file byte for byte, mismatch is a refusal that names the accept action of 07b; without a copy (new device) apply the mvp-06 bounds, work budget and cost confirmation and unlock the node's slot. The pull never stores the copy yet.
5. Authenticate `manifest.enc`; require `vaultId` equality with the slot file; caps; path policy over the whole manifest (decision 11); verdict (decision 4). Any failure aborts with nothing written. A `manifests/<...>` history target requires the inner `rootCID` to equal the named CID.
6. First-pull confirmation, then store the key-slot copy (only now), then raise the floor and write nothing else yet.
7. Plan with the three-way rule on plaintext sha256 (decision 7), ask the large-pull confirmation if the bytes to fetch exceed the ceiling (decision 14), then fetch and verify each file (decision 14). Conflict copy first, then rename.
8. Write the state, emit events, release locks. **State written by a pull (C-07):** for a name target, `rootCid` = the immutable root CID the name resolved to, `key` = the configured publication key name, `mfsRoot` = the configured MFS root; for `--root-cid` and `--manifest` the state is written only when the target is not a restore (a restore leaves the state as decision 8 says), with `rootCid` = the named or resolved root. `manifest`, `sequence`, `manifestIdentity`, `unmaterialized`, `complete`, `devicesSeen`, `highest*` as decisions 2 and 7 say; `previousIdentity` = `null`; `keyslotsSha256` = the digest of the copy stored in step 6. With `rootCid` equal to the node's MFS root after a pull, the next publish does not count the state as unpublished work. If a publish journal exists for this root and its sequence is not above the pulled sequence, the pull moves it to `.ipfs-sync/journal-set-aside.<sequence>.json` and says so (a pending publish that lost to the pulled manifest cannot resume; without this the publish refusal in decision 10.3 would have no exit); a journal above the pulled sequence is left for publish to resume.
Blobs are read from the authenticated `rootCID` tree, never from `<root>/current/` of the mutable tree.

### 7. Outcomes, `complete`, baseline, carry-forward
Per path outcome: `fetched`, `unchanged`, `locally-modified`, `conflict`, `integrity-failed` (fetch error, size, header, AAD, authentication, sha256), `unfetched` (ceiling declined, gateway refused ranges for a large file, pool aborted, write failure), `policy-skipped` with `severity` and `class`:
- `expected`: the path is in the configuration folder or matches the exclusion list (what an older build's manifest contains);
- `unsafe`, class `shape`: a path shape an honest publisher never produces (traversal, absolute, backslash, control character, empty or dot segment, a protected folder name by fold key including `.obsidian/plugins/`, the state folder);
- `unsafe`, class `platform`: a path an honest publisher on another platform can produce (Windows forms, reserved names, 8.3 shapes, collision groups, file/directory prefix groups).

`complete = false` iff any `integrity-failed` or `unfetched`; `policy-skipped` never makes a pull incomplete. Exit code 1 (CLI) iff any `integrity-failed`, `unfetched` or `unsafe` skip; `expected` skips are listed and exit 0. The plugin notice uses the same split. A restore is different: it leaves `complete` as it was and only reports failed or skipped paths and exits 1 for them (decision 8).

**Baseline and carry-forward (Q-01, Q-02).** After a non-restore pull the baseline is built as follows. A path that is fetched, replaced, conflict-replaced or found unchanged takes the node's entry. A path that is `unfetched`, `integrity-failed` or `policy-skipped` of class `platform` also takes the node's entry and is added to `unmaterialized`. A path that is `expected` or `unsafe` of class `shape` is not in the baseline. Paths the manifest no longer lists are dropped from the baseline and from `unmaterialized` (local files are never deleted; remote deletions are reported). `mtimes` come from the caller after the write.

*Publisher rule.* The publish copies every `unmaterialized` entry into the new manifest unchanged, does not compare it with a local file (a local file at that path is not scanned as an edit, and is listed as "not published: this device holds no current copy"), does not count it as a removal, and counts its blob as named in the drift check. A carried path that now matches this device's exclusion list is dropped (exclusion wins). The consequences: a Linux-written `CON.md` or a `Note.md`/`note.md` pair survives a Windows device's publish (the path policy refuses `CON.md` on every host, so no pull restores it, a Linux pull included; it is carried and the pull exits 1 for it); a file the gateway could not deliver to a plugin stays in the vault for every other device; `complete: false` no longer has to block publish, so a gateway that ignores `Range` cannot lock a device out for ever. `expected` and shape-unsafe entries are not carried: an entry under `.obsidian/` from an older build, or a forged traversal entry, leaves the manifest at the next publish (the entries removed because they are excluded are listed and, in 07b, counted apart from other removals).

*Next pull.* For a path in `unmaterialized` the three-way rule runs with `B` absent: a missing local file is fetched, a local file equal to the node's content makes the path restored, and a local file that differs becomes a dated conflict copy and the node's text takes the path (a stale older copy of an `unfetched` file produces one extra conflict copy; accepted).

*Stated costs.* A device that never manages to restore a path keeps an entry it cannot vouch for in every manifest it publishes; an `integrity-failed` path keeps pointing at the node's bad blob; both are reported at every pull with exit 1.

### 8. Restore
A restore is a pull with verdict `restore`. The state is not touched except: `restoredFrom` (lowest accepted sequence) and `devicesSeen`; `manifest`, `sequence`, `manifestIdentity`, `unmaterialized`, `highest*`, `complete`, `rootCid` stay as they were, and `mtimes` of restored paths are dropped. `complete` is not recomputed for a restore: a file that fails during a restore is reported and makes the command exit 1, and the baseline does not describe the restore. The three-way rule runs with the existing baseline as `B`. So after a restore the local files differ from the baseline, and the next publish sees them as changes and publishes them as a new, higher sequence (`sequence = node + 1`). This replaces the first draft's "record describes the restored manifest", which contradicted `decodeRootState` and made the publish scenario impossible.
- A plain pull after a restore finds `B == R` and `L != B` for restored files and leaves them (`locally-modified`); it does not undo the restore.
- Restore never deletes: files that did not exist in the older version stay. Stated in the UI, the command output and the docs.
- A directory with no state uses the floor as record; a restore there (explicit older target, floor higher) is accepted with the flag and creates a state whose baseline is the older manifest; publish then finds the node ahead and says "pull first".
- **Plugin Restore list (Q-06).** The list shows names and, for entries of at most 8 MiB, the decrypted sequence, date and device. Names are not authenticated. After the user picks an entry and before the confirmation dialog, the plugin loads and authenticates that entry's manifest and shows its authenticated sequence and date in the dialog; if they differ from the label in the list, it refuses and says the history entry does not match its name.

### 9. Fork resolution (`pull --resolve-fork`)
Situation: this device published sequence N+1 (its state records identity X) and the node now serves sequence N+1 with identity Y (another device published at the same time; the later `name/publish` won). Conditions: target is the name; the node manifest authenticates; same `vaultId`; equal sequence and different identity; the fork is not older than the record.
Steps: authenticate Y; find the common ancestor manifest (sequence N) from history by name prefix `N` through `history-names.ts`: **exactly one** history entry may carry prefix `N`, it must authenticate with the same `vaultId` and sequence N, and its identity must equal this state's `previousIdentity` (the manifest this device built on). If there are two or more entries at prefix `N` (an earlier fork), none, a mismatch, or `previousIdentity` is `null`, use no ancestor (Q-03, C-08). Three-way plan: `B` = ancestor entry (or absent), `L` = local file, `R` = Y's entry. With an ancestor, a file edited only here stays (`locally-modified`), a file edited only there is replaced, a file edited on both gets a conflict copy. With no ancestor, every file that differs from Y becomes a conflict copy (the local text is kept, Y's text takes the path). The local baseline (X) is not used as `B`, because `L == X` would make `replace` overwrite this device's edit without a copy. After the fetch: `manifest`/`sequence`/`manifestIdentity` become Y's, `highest*` keep the sequence and take Y's identity, the floor is rewritten with Y's identity (the only operation that changes an identity at a sequence), `unmaterialized` and `complete` per decision 7, `previousIdentity` = `null`. The next publish is sequence N+2 and includes this device's local-only files. `--resolve-fork` needs an interactive confirmation (plugin: dialog) that states what happens. It cannot be combined with `--allow-rollback`, `--root-cid` or `--manifest`.
This is a recovery, not a merge: the other device's edit and this one's both exist after it (one as a conflict copy) and the orphaned X manifest stays pinned in the node's history.

### 10. Publisher deltas (second-device publish)
1. **Ahead and new device.** `sequenceAhead` text changes to "another device published sequence N; run pull first" and stops naming `--repair` for a device with a baseline. `vault-keys.ts` `new-device` text changes to name pull. `sequenceFork` text names `pull --resolve-fork` instead of abandon. **`--repair` for `ahead` (Q-07):** refused when a floor exists for the vault's `vaultId` (read from the node's key-slot file; the message says pull first), and refused when the device has a state that decodes for the same vault. It is offered, behind its existing confirmation whose warning recommends pull first, only when the state file exists and does not decode (`RootStateError`) and no floor exists for the vault. A device with no state and no floor is a new device and is told to pull. `behind` and rebuild repairs are unchanged. (Decision: `--repair` for an unreadable local record is how `RootStateError` tells the user to recover; removing it altogether would leave no route for a corrupted state file. Open question 7.)
2. **Incomplete pull.** Superseded by the carry-forward of decision 7: publish does not refuse on `complete: false`. There is no `last-pull-incomplete` refusal.
3. **Concurrency detection.** When a publish has work, it resolves the owned name with `nocache` and a short `dht-timeout` (`NAME_RESOLVE_TIMEOUT`, proposal `10s`) before its first write and records `startRoot`, and resolves again immediately before `name/publish` (in `publishRoot`, after the key-list check).
   - *Classification (C-03).* `src/kubo/ipns.ts` returns one of `value`, `not-found`, `failed`. kubo reports a missing record and a routing timeout through the same error class, so the classification compares the error text with a table held in that one file; anything not in the table is `failed` (fail closed). The table is filled from the operator's node in task 2.2; the strings are not asserted here. `CommitClient` gains `nameResolve` and the commit port gains `resolveName`.
   - *Rules.* (a) A key created by this run is not resolved at either point. (b) Otherwise `failed` at either point is a refusal that names routing as the cause; `not-found` at the start needs `not-found` at the end; a value at the start needs the same value at the end. (c) Exception, stated as a residual: on the first publish of a vault (no node `manifest.enc`, no local state), a timeout counts as `not-found`, because a never-published name produces a timeout and refusing it would block every first publish on a slow DHT; two devices' first publishes cannot then be told apart.
   - *Journal (Q-04).* `startRoot` (a CID or `null` for "no record") is stored in the publish journal when the pending manifest is built (`JOURNAL_VERSION` becomes 2; the decoder accepts 1, where `startRoot` is unknown and the state's `rootCid` stands in). Resume compares the name's current value with the journal's `startRoot` before it adopts the pending manifest and before any `name/publish`; a difference is `overlappingPublish`: nothing is published, the tree stays as written, the journal stays. The next pull moves that journal aside (decision 6 step 8) when it pulls a manifest at or above the journal's sequence.
   - *Limits.* This narrows the overlap to the time between the second resolve and `name/publish`; it is not a compare-and-swap, kubo offers none, and a write race on the shared MFS `current/` tree is not detected at all. Stated loudly in the docs: overlapping publishes are detected at a later pull.
4. **Drift path and other devices.** `diagnose` (`drift.ts`) still computes `strays` (blob-shaped files the new manifest does not name; carried entries' blobs count as named). The publisher removes them only when `devicesSeen` holds no device other than its own and the node's latest manifest names this device. Otherwise it reports them and removes nothing. The guard protects a device only after it has seen another device's manifest; the first overlap can still make the other device's read-back fail, which fails that publish and is retried. No node-side device marker is added (considered: a marker file on the node; deferred).
5. **C5-02.** `PublishOptions` gains an optional async `beforeFirstWrite?: () => Promise<void>`. It is awaited, as a fresh check each time (not memoised), at the three places where a run first can write: before `resumeJournal` in `openSession`, before `clearJunk` in `history-gate.ts` (only reachable under `--repair`), and in `transfer` before `key.ensure()`. The plugin runner passes `checked.verifyHeld` (`lock-token-check.ts`) wrapped to throw `lockHeld`; the CLI passes a file-read token check. Additive and optional; a host that passes nothing behaves as today. This closes review-5c C5-02 to the extent the token file is authoritative; it is still a check-then-write, not a mutex.
6. **Device label.** From decision 3.
7. **Carry-forward.** From decision 7: the plan copies `unmaterialized` entries unchanged; `idle-check.ts` counts only materialized entries when it compares the scan with the record.

### 11. Path policy (`path-policy.ts`, pure)
Applied to the whole authenticated manifest before any blob is requested, and again at write time. The full policy is not applied inside `decodeManifestFile`, because the publisher decodes its own manifests and a legitimate Linux vault can hold names the pull must refuse on every host, Linux included (for example `CON.md`). Review 6.4 (B1-03) found that the decoder does apply a strict shape check (`untrustedPathReason` through `checkPath`: control characters, `..`, absolute forms, backslash, lowercase `.ipfs-sync`), and that is intended: one path that fails it refuses the whole manifest as `manifest-unsupported`, on every device, and fails closed. The policy's `unsafe`/`shape` skip, carry-forward and `needsAttention` outcomes apply to paths that pass the decoder; for the decoder's own cases they are reachable only as policy-level vectors. The trade-off is that one forged entry makes the vault unpullable and unpublishable until the manifest is replaced (spec `path-hardening`, "Decoder strictness"). The same holds for the path limits of `src/sync/path-limits.ts` (4096 path bytes, 255 bytes per segment, 128 segments; B1-01): the decoder refuses a manifest holding a path over them, so a vault with such a path cannot be published. This is intended (spec "Path limits"). The publisher gets an advisory warning listing paths other devices will not restore.
- **Fold key** (`path-fold-table.ts`, Correction 2 / C-02). Steps, repeated until stable (at most 3 passes): NFKC; per-code-point case folding from a generated table (Unicode `CaseFolding.txt` statuses C and F); the supplement below; removal of code points with `Default_Ignorable_Code_Point` (from the same generated file). Supplement: U+0131 maps to `i`, and a U+0307 that directly follows `i` is removed, so that `.ıpfs-sync` (U+0131, which NTFS's upcase table aliases to `I`) and `.İpfs-sync` (U+0130, which folds under status F to `i` plus U+0307) both reach `.ipfs-sync`. The table is produced by `tools/gen-path-fold-table.mjs` from a pinned Unicode version, recorded with the sha256 of each source data file in the header of the generated `src/sync/path-fold-table.ts`, which is checked in and never edited by hand. JavaScript has no built-in full case folding, so the table, not the host's `toLowerCase`, is the definition; `String.prototype.normalize` is still the host's, which is a stated residual across Unicode versions. A unit test checks the vector list against the table and checks the header fields; a second test fails when the file differs from its recorded body hash. The compared names are `.ipfs-sync`, `.obsidian`, `.git` and, in the plugin, `vault.configDir`. The compared segment is the first segment of a path, and any segment for `.git`.
- **Windows forms** (refused on every host, because the vault may be synced to Windows): trailing dot or space in a segment; `:` in a segment (alternate data streams, `::$DATA`); reserved device names `CON PRN AUX NUL COM1..COM9 LPT1..LPT9` and their superscript-digit forms, with or without an extension, after the fold; **8.3 short-name shapes (Q-09):** a segment matching `^([^.~/]{1,6})~[0-9]+(\.[^./]{0,3})?$` (case-insensitive) whose captured prefix, after the fold key, is a prefix of the fold key of a protected folder name without its leading dot (`obsidian`, `ipfs-sync`, `git`, the configuration folder). So `OBSIDI~1`, `OBS~1`, `GIT~1` and `IPFS-S~1` are refused and `abc~1.md` is accepted. The vectors include all four refused forms and the accepted one.
- **Collisions**: any two or more manifest paths with the same fold key (case or normalisation), and any path that is a file while another manifest path lies beneath it, are refused as a group. Policy: all members of the group are skipped with `severity: unsafe`, class `platform`. Honest Linux vaults with `Note.md` and `note.md` are therefore not restored on any device; the message says which to rename on the originating device.
- **Realpath containment** (Node CLI only): before every create, write and rename, the parent directory's realpath must be inside the realpath of the vault root. The existing `findSymlink` prefix walk (`symlink-guard.ts`) stays. The Obsidian adapter cannot see symlinks; stated as a residual, not fixed.
- **Path limits on the publisher side.** The limits (4096 bytes, 255 bytes per segment, 128 segments) also apply to the publisher's own manifest, so a local path over a limit makes the publish refuse with a message that names the local path and the limit (spec `path-hardening`, "Over-limit local path on the publisher side"). On common filesystems 255 bytes per segment is the Linux limit, and a very long non-ASCII title (about 85 CJK characters at 3 bytes each) reaches it.
- **Output**: no message contains a path on the `unsafe` list beyond the first 3 names and a count; control characters (C0, C1 including U+009B, bidi overrides) in any shown path are escaped (P-16).
- **Exclusion matching (Q-01, C-11).** The fold-aware comparison is used by `path-policy.ts` for the protected names and by a pull-only matcher `createPullExclusionMatcher` in the same module for the effective exclusion list. The publisher's `createExclusionMatcher` in `exclusions.ts` is not changed by this change (it compares segments exactly, as today), so what the publisher, the scan and `idle-check.ts` exclude does not change; a test holds that matcher to a vector list before and after. `pull-plan.ts` (v1) is unchanged.

### 12. Default exclusions
`DEFAULT_EXCLUSIONS` gains `.obsidian/` (replacing the six narrower `.obsidian/...` entries, which it contains). The plugin adds `vault.configDir` as an extra exclusion when it differs from `.obsidian`. The CLI documents adding a renamed config folder to the exclusion list. The effective list changes, so `excludesHash` changes for every vault; the pull warns once per manifest whose `excludesHash` differs, exactly as the v1 pull does (`forceVerify`: every local file is verified by content and nothing is deleted). Paths from old manifests under `.obsidian/` are `policy-skipped`/`expected`; they are not carried forward, so the first publish after the upgrade removes them from the manifest (07b counts them apart from other removals). Whitelisting non-plugin `.obsidian/*.json` for sync is a later product question.

### 13. History names
Publisher writes `manifests/<16-digit zero-padded sequence>-<cid>.enc` (sequence up to 2^53-1 has 16 digits, so lexicographic order equals numeric order for every valid sequence). Readers (`history-check.ts`, `read-back.ts`, pull `--manifest`, listing) accept `^(?:[0-9]{16}-)?[A-Za-z0-9]{10,128}\.enc$`; `tools/feature-op-mvp-06/policy.mjs` carries its own copy of the old rule and is updated in task 1.4 so that its dry run still passes (C-09). Legacy names sort before every prefixed name and have no order among themselves. `ensureHistoryFile`: a prefixed file that already exists with other bytes is replaced only if it authenticates, has the same vault and sequence and the same manifest identity (a resume that re-encrypted); any other difference is `history-conflict`. A name beginning with a prefix whose decrypted sequence differs from the prefix is treated as planted by listing code (it is skipped in restore lists and prune refuses). The dependency for 07b: `prune-history` and the restore list use this order; 07b must not start its prune task before 07a task 1.4 closes.

### 14. Blob fetch and resource bounds
- **CLI**: streaming from `gatewayStream` (no range). Per file in flight: one plaintext segment and one ciphertext segment. A 100 MB file never holds more.
- **Plugin transport fact (C-04).** `requestUrl` buffers the whole response before it returns, so a streaming read of the plugin's `Response` does not bound memory. Nothing in this design claims that a body is "not buffered" in the plugin; where a response is refused the wording is "discarded, not decrypted".
- **Plugin ranged fetch**: the plugin fetches segment-aligned ranges: header first (`bytes=0-21`), then segment `i` at `22 + i*(2^e + 28)` for `2^e + 28` bytes (last segment short). Each response must be 206 with a `Content-Range` whose start, end and total match the request and the expected blob size `22 + 28n + size`; otherwise the file is `unfetched` (not integrity-failed) with a named reason. A 200 answer to a range request is accepted only if the expected blob size is at most `WHOLE_BODY_LIMIT = 32 MiB` (two largest segments); above that the file is `unfetched` ("gateway ignored Range; file too large to fetch in this host"). Exponent comes from the header; an exponent above 24 is an integrity failure before any further request, and an exponent below `PLUGIN_MIN_EXPONENT = 20` makes the file `unfetched` in the plugin ("segment size too small for ranged fetch here"; exponent 16 would mean 16,384 requests per GiB; a proposal, not a measurement; the CLI streams and is not limited).
- **Range probe and early failure (C-04).** The plugin requests the header range of the smallest blob to fetch first, alone, before any other ranged request. A response to a header request that holds more than `22 + RANGE_PROBE_MARGIN_BYTES` (proposal 64) bytes, or that has status 200, marks the gateway `range-ignored` for the whole pull: every later file whose expected blob size exceeds `WHOLE_BODY_LIMIT` becomes `unfetched` with no request, and files at or below the limit are fetched whole. The probe bounds the memory exposure to the smallest blob's own size; the plugin does not advertise large-file pull until the 07b operator run records the outcome (`range-honoured` or `range-ignored-refused`).
- **Memory budget**: in-flight plaintext plus ciphertext across the pool is at most `SEGMENT_MEMORY_BUDGET = 128 MiB`; concurrency is `min(6, floor(128 MiB / (2 * (2^e + 28))))` per file class, so 6 at exponent 23 and 4 at exponent 24. Constants are proposals, not measurements.
- **Total bytes**: the sum of sizes of files that must be fetched is computed from the manifest before the first byte is requested. Above `PULL_CONFIRM_ABOVE = 512 MiB` (plugin setting `pullConfirmAboveMb`, task 5.0; CLI `--max-bytes`) the pull asks (plugin dialog; CLI prompt or refusal unless `--accept-large`). Declined means `unfetched`, `complete: false`, nothing fetched.
- **Disk**: free space is checked only where a host provides an optional `freeBytes` port to the pull: the CLI passes one built on Node `statfs`. `HostFs` has no such call and the obsidian typings used here have none, so the plugin passes no port and performs no free-space check; the earlier wording that the host "exposes" one is dropped. The plugin relies on the ceiling, the temp sweep and a typed handling of a write failure: the `.part` file is removed and the file is counted `unfetched` with the reason "could not write", not `integrity-failed`, so a full disk is not reported as tampering.
- **Temp files**: `.ipfs-sync/tmp/<random>.part`, plaintext at rest until renamed or swept. Swept at every pull start under the lock, at CLI start for `pull`, and at plugin load. The plugin-load sweep (Q-11) runs only while it holds `publish.lock` (a try-acquire; if the lock is held, for example by a CLI pull on the same vault, it skips), so it cannot delete the `.part` file of a live pull. Listed as a limit. The final rename uses the host `rename`, which in the plugin removes the target first (not atomic): a crash in between leaves the destination missing; conflict copies are made before the replace, so a local edit survives, and an unedited file is recoverable from a pinned root. If a conflict copy cannot be written (for example a name that is too long), the replace of that file is aborted, the file is counted `unfetched` with that reason, and the local file is left as it was (Q-11).
- **W-16 (single-read upload source)**: the Obsidian `readRange` reads the whole file once per upload and serves the segment reads from that copy; it checks size and `mtime` before the first segment and after the last and throws a typed `file-changed-during-read` error if they differ, so a file edited during an upload is skipped this run (the next run sees the new mtime) instead of being uploaded as a mix of versions. Memory: one copy per file in flight, bounded by the read cap as before. Why it is in this change (C-09): the plugin becomes a second device that edits the same vault concurrently, which is when a torn upload (a blob mixing two versions, with a manifest hash of neither) becomes likely, and the deferred item was assigned to this change by the operator's decision log entry. Its task has no Requires and can be moved without touching any other task.
- **Mtime shortcut**: the pull skips hashing a local file whose size and mtime equal the baseline's (as publish's `diff.ts` does). A file whose content changed with the same size and a restored mtime is trusted. Accepted limit.

### 15. Plugin specifics
Pull runner takes both locks (decision 6). Second-device onboarding is documented and hinted in the dialog: the second install must (a) use the same MFS root and publication key name, (b) adopt the owned publication key through the existing key-adoption flow (`key-adoption.ts`, `adopt-key-dialog.ts`) before it can publish, and (c) pull before it publishes. Pull itself needs neither the key nor a write to the node. The pull-name field accepts `/ipfs/<cid>` (task 5.0). Node-supplied text is rendered with `textContent` only, never `innerHTML`, and the plugin adds no clipboard-copy control for node-supplied text or secrets on any platform (Q-11).

### 16. Marker rule in 07a
The guard is untouched. The encrypted pull calls the existing `assertPullDestination` (CLI) and `assertVaultPullDestination` (plugin) first; a destination that is absent, empty, or carries a fixture marker is accepted, and the pull writes `pulled-fixture` when it populates an empty one (`writeFixtureMarker`). `assertPublishMarker` accepts only `fixture`, so a directory produced by pull cannot publish until the user replaces the marker text by hand; the refusal already carries that hint (`MARK_FIXTURE_HINT`). Two-device tests and the integration suite set the marker explicitly. The refusal texts in `pull-guard.ts` that say the pull "refuses encrypted roots, and decrypting pull arrives in a later release" become false in 07a and change to "pull into a populated directory without a fixture marker stays disabled in this build"; that is a wording change, not a policy change. 07b replaces the whole mechanism.

### 17. Wrong passphrase and first-pull trust
Unchanged from the first draft where still correct: one typed outcome for wrong passphrase, damaged slot and failed commitment with identical work; no lockout; distinct non-oracle errors for a missing slot file and for a manifest that fails authentication after a successful unlock; `passphrase-format` errors before any derivation. Additions: a root holding `keyslots.json` and no `manifest.enc` (or a 404 on it) is refused as "key slots without a manifest (withheld or not yet published)", neither treated as an empty vault nor used to create anything; a planted `manifest.json` next to an encrypted layout is never read (the v1 reader stays until 07b but is not reachable when `keyslots.json` exists).

## Risks / Trade-offs

- [Floor and state disagree after a crash] -> floor is written first; disagreement at an equal sequence is treated as `fork` and recovers via `--resolve-fork`.
- [State v3 breaks dev builds that wrote v2] -> upgrade on read; old builds refuse v3 (fail closed); no released build is affected.
- [A device publishes with paths it cannot restore] -> carry-forward copies the node's entries; the cost is that a device which can never restore a path keeps vouching for it, and pull exits 1 on it every time (decision 7).
- [Collision policy refuses honest Linux vaults] -> documented; message names the paths; carry-forward keeps them in the vault; open question 2.
- [`--repair` ahead narrowing removes a recovery] -> kept for an undecodable state with no floor; open question 7.
- [Fork resolution with no ancestor makes many conflict copies] -> only files that differ from the other side; the ancestor is used only when exactly one entry at the prefix authenticates and matches `previousIdentity`.
- [Publish re-resolve adds latency and a failure mode] -> one read-only request each, bounded by `NAME_RESOLVE_TIMEOUT`; a failure refuses and resume adopts or the next pull sets the journal aside; measured at the 07b operator run.
- [Name-resolve error text is not classified by this document] -> unrecognised text is `failed` and refuses (fail closed); the table is recorded from the operator's node.
- [No hashing of `manifest.enc` bytes] -> equality on the plaintext identity; a node that re-encrypts nothing cannot create a false fork.
- [Ranged fetch unverified against `requestUrl`] -> refusal paths are typed (`unfetched`), the probe bounds the first exposure, the 07b operator run asserts a multi-segment blob; if Range fails, plugin pulls of files above 32 MiB are refused and the docs say so.
- [The uncomfortable one] The carry-forward rule means this device's publish vouches for content it has not seen. If the node serves a wrong-but-authentic entry for a path this device could not restore, the next publish republishes that entry under a new sequence and this device's name, and there is then no record that the device never held it beyond `unmaterialized` in its local state.

## Migration Plan

States of format 2 upgrade on read and are rewritten as 3 on the next state write. Journals of format 1 are read as before (`startRoot` unknown) and rewritten as 2. History files named `<cid>.enc` remain readable and are never renamed. The default exclusion change alters `excludesHash`; every device sees one "exclusion lists differ" warning per old manifest. The v1 reader, `--allow-plaintext-v1`, `--manifest-file` and the latch stay until 07b. Rollback: `git revert` restores mvp-06 behaviour for the code; a v3 state then needs the operator to abandon or re-pull.
