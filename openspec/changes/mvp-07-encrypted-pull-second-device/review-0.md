Reviewer: security-reviewer. Static read only (Read/Glob/Grep); nothing executed; single-model review (cross-model judge not run). Read proposal.md, design.md, tasks.md, all nine specs, plus the mvp-06 design/specs/reviews and the delivered code. Saved by the lead as a condensed record (2026-09-30); every finding id, location and fix is kept.

VERDICT: PROCEED-WITH-FIXES — 0 critical, 4 high, 11 medium, 6 low. Nothing reaches real notes while the marker guard holds, so no CRITICAL; P-03 and P-04 would be CRITICAL if the guard were lifted as designed. Fold the HIGHs into design.md and the specs before tasks 2.2, 2.3, 2.5 and 4.2 start. The plan's own two-device scenarios (P-01, P-02) produce silent data loss and permanent lockout without any hostile party; the reviewed-code guarantee (P-03) is not what the checker measures.

## HIGH
- **P-01 — a pull that partly fails advances the sequence record; the next publish then drops files.** design.md decision 2 step 8, rollback-detection "Record of the highest sequence", second-device-publish, encrypted-pull "Fetch and verify every file". The record is written "after the pull has processed the manifest" even when files failed; the state `manifest`/base is unspecified for failed files. A node that flips a bit, 404s or stalls one blob makes that file fail on device B; B still records sequence N; B's next publish passes the up-to-date rule and, with the file absent locally, publishes N+1 without it; the mass-removal guard fires only above 50%. Compounding: mvp-06's publisher does not exclude `.obsidian/app.json` etc. (`DEFAULT_EXCLUSIONS` covers only workspace, cache, plugins) while pull refuses `.obsidian/` (`pull-plan.ts:27`), so every honest manifest contains entries pull counts as failed and a failure-based publish block would wedge. Fix: split outcomes into `integrity-failed` and `policy-skipped`; record `complete: false` on any integrity failure or unfetched file and refuse publish until a later pull completes; the state `manifest` must equal what is on disk; add `.obsidian/` (the real `vault.configDir`) to the publisher's default exclusions in this change; test: one bad blob then publish must refuse and not remove the file.
- **P-02 — two devices publishing concurrently: silent lost update, then permanent fork lockout with no recovery path.** second-device-publish "Up-to-date rule", "Multi-publisher guard"; rollback-detection "Refuse forks"; decision 9; open question 8; task 2.5. Both devices share one node, one MFS working tree and one IPNS key; the lock file is per vault so it does not serialise them. A and B both read N, both pass the client-side rule, both write blobs into the same `current/`, each writes `manifest.enc` (last writer wins) and calls `name/publish`; two manifests exist at N+1; the loser's edits are absent from the name; a later pull on the loser hits "equal sequence, different content", refused and "never overridable" — wedged; only abandon or deleting `.ipfs-sync/` gets out and that discards the baseline. The multi-publisher guard protects only a device that has already seen another device's manifest; B, whose own manifest is latest, still deletes A's in-flight blobs on its drift path. Task 2.5 tests only turn-taking. Fix: re-resolve the name with `nocache` immediately before `name/publish` and require it equals the root the publish started from (narrows, not a compare-and-swap); an explicit fork resolution `pull --resolve-fork` (authenticate the node manifest, three-way plan against the local base with conflict copies, keep the record so the next publish is a higher sequence; not silent, not overridable by `--allow-rollback`); the drift path never deletes unnamed blobs unless the device knows it is the only publisher (record every `device` seen); state loudly that concurrent publish is detected only at a later pull; concurrent-publish test and a "cannot" line in the release notes.
- **P-03 — "reviewed code = shipped code" is false as designed.** decision 11, guard-removal "Precondition A" and "What removal changes", open questions 4 and 5, tasks 2.1 and 6.3. The tree hash covers only `src/` and `cli/` minus two files; it omits `package.json`, `pnpm-lock.yaml`, esbuild and tsconfig, `manifest.json`, `tools/` (checker, feature-op) and the built bundles (open question 4 says "include" but no task does). Removal is said to replace two modules and change "nothing else", yet policy references sit in 14 files / 54 hits in `src/` and `cli/`: `src/core/config/node-safety.ts` (`assertFixtureVault`, `classifyMarkerText`, `markerProblem`), `defaults.ts`, `pull.ts`, `pull-notices.ts`, `publish-notices.ts`, `settings-tab-copy.ts`, `vault-opener.ts`, `publish-runner.ts`, `pull-runner.ts`, `publish-session.ts`, `cli/publish-command.ts`, `cli/init-command.ts`; task 6.3 also removes the exported check from shared config. Either those edits change the hash (post-removal tree is not the reviewed one) or they are unreviewed extra changes; UI copy saying "fixture only" would survive. Fix: make the removal a real diff on a branch before the review and the operator run (the operator run uses throwaway vaults anyway); the reviewer reviews the actual post-removal tree and records `Post-removal-tree-sha256` covering `src/`, `cli/`, `package.json`, lockfile, build config, `manifest.json`, `tools/check-guard-preconditions.mjs` and `tools/feature-op-mvp-07.mjs`; bind the sha256 of the built `main.js` and CLI bundle from a reproducible production build of that tree; the release tool asserts the shipped bytes equal them; gate release, not code; specify the hash scheme exactly (LF bytes, code-unit path order, `git ls-files` set, no symlinks, no name-based excludes that let code hide, e.g. `*.test.ts` under `src/`).
- **P-04 — each of the three guard-removal preconditions can be forged, stale, or satisfied by unrelated evidence.** A (review file): plain-text lines (`Verdict: APPROVED`, `Open high: 0`) any writer can produce; a count line can contradict findings in the body; nothing binds the file to a real review; the checker is unreviewed code. B (run result): `<tmp>/ipfs-sync-feature-ops/feature-op-mvp-07.json` in a world-writable temp dir; self-attested JSON; `codeTreeSha256` is the source hash, not the sha256 of the `main.js` installed in Obsidian (same class as R5-10); the script that writes the assertions lives in `tools/`, outside the hash; no freshness bound, no owner check. C (phone timing): the acceptance is a line in the agent-writable decision log, so the beneficiary can write it; a timing file needs only model, OS and seconds — no `completed` flag, no threshold, a failed or out-of-memory run could be recorded; the screenshot is not checked. Fix: A — detached signature (SSH-signed, the mechanism the adversarial-review waiver uses) or a review file committed before the removal commit and unchanged afterwards; machine-readable findings block with statuses; record the checker's own sha256 in the review. B — 0700 per-user directory with owner check; record sha256 of installed `main.js`, `manifest.json`, `styles.css` and the CLI bundle; include the script in the hash; age bound. C — acceptance only through an interactive TTY step in `tools/record-phone-timing.mjs` (typed phrase, nonce printed by the tool) or a signed statement; a timing record needs `completed: true` and the plugin build hash.

## MEDIUM
- **P-05 — sequence record versus restore and the state invariant.** rollback-detection "Deliberate restore", decision 3, `root-state.ts:57`. `decodeRootState` requires `state.sequence == manifest.sequence`; the spec wants `state.manifest` to describe restored (lower) content while "highest sequence" stays 5 — cannot both hold; which value the up-to-date rule uses is unspecified; until a publish, a plain pull re-applies sequence 5 and silently undoes the restore. Fix: separate `highestSequence` and `highestManifestSha256`; publish uses `highestSequence`; state next-publish behaviour.
- **P-06 — baseline resets without a signal.** decisions 3 and 10; tasks 2.4, 2.5. `abandon` moves `state.<h>.json` aside; deleting `.ipfs-sync/` or changing the configured `mfsRoot` (state file name is a hash of it) does the same; the next pull is a "first pull" with no baseline, defeating "fork never overridable" and "record never lowered"; once the latch stops being consulted (P-14) nothing remains of the R5-02 evidence. Fix: a `sequence-floor` file outside the moved set keyed by `vaultId`; a first pull after `abandon` or with an `abandoned-*` backup present shows the abandoned sequence and refuses lower without `--allow-rollback`; key the record by `vaultId` plus directory, not by the `mfsRoot` setting.
- **P-07 — first-pull trust: the user sees nothing.** decision 5, open question 2, encrypted-pull "Unlock on a device that did not create the vault". A hostile node chooses which genuine old state a new device gets and can mix a genuine old `keyslots.json` with a current manifest (same VCK), yielding only a wrong-passphrase message; the gateway path never verifies bytes against the CID, so `/ipfs/<cid>` and `--root-cid` bind nothing client-side and the proposal's "for verification" claim is empty. Fix: show sequence, `publishedAt` (authenticated) and `device` on every first pull with a confirm; add `--expect-min-sequence` and `--expect-vault-id` now; state that root CID trust rests on the gateway.
- **P-08 — `--allow-rollback` is not scoped to explicit targets.** rollback-detection "Refuse lower sequences", "Deliberate restore". The refusal message names the flag, training users to add it after a stale served state. Fix: accept only with `--root-cid` or `--manifest` (plugin: only from the restore action); name-resolved lower-sequence refusals do not suggest it and say the node may be stale or hostile.
- **P-09 — accept-changed-slots proves the key, not slot freshness; read/write atomicity unstated.** key-management "Other devices must accept changed key slots", decision 8. The manifest authenticates the VCK and any genuine slot for the same VCK passes; the sequence rule is not stated to apply to accept; fetches must come from one resolved immutable root CID and the copy written must be the exact bytes that unlocked; accept must update `keyslotsSha256` in state and the journal; `--root-cid` restore across a rewrap boundary needs the old slot and cannot work with the byte-compare rule. Fix: state each; restore across a rewrap goes through accept with a downgrade warning that shows the older cost.
- **P-10 — rewrap details.** key-management "Change passphrase by rewrap", "Increase key-derivation cost", decision 8. Unstated whether the new `keyslots.json` replaces or appends (appending leaves the old passphrase valid in the current root and exceeds the two-slot try budget) — state replace; the "Standard" preset can silently lower cost from High — require new cost >= current or an explicit downgrade confirm; increase-cost with the same passphrase does nothing against an attacker holding the old pinned cheaper slot — say so in the UI or require a new passphrase; two concurrent rewraps: last write wins and the loser's saved passphrase stops opening the current slot — add a post-publish test unlock of the node's `keyslots.json` with the new passphrase and warn when another device's rewrap is detected.
- **P-11 — path hardening is whack-a-mole and misses collisions.** encrypted-pull "Refused paths"; decisions 6, 6a; task 2.3; `manifest-paths.ts`, `exclusions.ts`. Enumerating U+0131/U+017F is incomplete — use NFKC plus full case folding plus removal of default-ignorable code points, compared against `.ipfs-sync`, `.obsidian`, `.git` and the real config directory (`vault.configDir`, which can be renamed); where a realpath is available (Node CLI) verify containment by realpath; `isExcluded` is case-sensitive (`.Git/hooks/x` lands in `.git/hooks` on macOS/Windows). Missing: Windows reserved device names (CON, NUL, AUX, COM1.., LPT1.., with or without extension); paths differing only by case or Unicode normalisation (silent overwrite then a publish that drops one file); file-versus-directory prefix collision. The Obsidian adapter cannot see symlinks (`obsidian-fs.ts` header); after the guard is lifted pulls run in real vaults that may contain symlinked folders — on desktop use Node `lstat`. Fix: add all as spec and task scenarios.
- **P-12 — resource-exhaustion claims do not hold in the plugin.** encrypted-pull "Files streamed"; decision 7; open question 12; task 3.1. `requestUrl` buffers whole responses (W-06); "one segment in memory" holds only for the CLI; six 16 MiB segments in flight is ~192 MiB (plaintext plus ciphertext), not 96 MiB; no cap on total bytes or per-file size; no disk-full policy (ENOSPC leaves temp files until the next sweep); restore-history listing decrypts up to 20 manifests of up to 64 MiB each. Fix: segment-aligned ranged fetch in the plugin (offset 22 + i(2^e+28)); abort when a gateway answers 200 to a Range request and the size exceeds the cap; configurable total-bytes ceiling with confirm above it; free-space check where the host exposes it; a smaller cap for history listing; sweep temp files on plugin load.
- **P-13 — the equal-sequence rule compares ciphertext hashes and has a gap for old state.** rollback-detection "Refuse forks"; decision 3. mvp-06 state has no hash, so at an equal sequence with different content the pull records it silently. Fix: for unrecorded hashes compare `manifest.rootCID` and the file map to `state.manifest` and refuse on difference. `manifest.enc` uses a random nonce, so a re-encryption at the same sequence (resume, repair, W-04) is a false fork forever — hash the canonical plaintext manifest or compare `rootCID` plus the file map as the equality test.
- **P-14 — plaintext removal and latch role: three loose ends.** plaintext-removal; decision 10; tasks 2.4, 2.1. A root with both a planted `manifest.json` and encrypted files must take the encrypted path and never read `manifest.json` (add a test); behaviour when `keyslots.json` exists but `manifest.enc` is absent or 404 (withheld) is unspecified — refuse, neither treating the vault as empty nor creating anything; guard-related notices and copy (`FIXTURE_ONLY_PULL_NOTICE`, settings copy) survive removal (P-03); removing the latch consult without a replacement for the R5-02 evidence is covered by P-06.
- **P-15 — Release 2 and the dist check.** release-2 "Two variants", "Release build is checked for test hooks", "Tool behaviour"; decision 13; tasks 4.4, 4.2. Variant A depends only on the checker and two module hashes; the tool "copies artifacts unchanged from the build output" without requiring a fresh production build from the recorded tree — a stale `dist/` from before a post-review edit ships under a "usable on real notes" claim; the guard-removal spec lists the dist check but decision 11 and task 4.2 do not put it in the checker; `checkDistBundles` scans only `main.js` and the CLI bundle and only for existing sentinels — a new test hook without a sentinel passes; the "cannot" paragraph omits concurrent-publish forks and lost updates (P-02), deleted notes staying in pinned old roots forever, `.obsidian` configuration and plugins not synced, and `.ipfs-sync/` being plaintext at rest including temp files (P-17). Fix: rebuild inside `record`, record tree hash and bundle hashes, refuse on any mismatch; add the dist check to the checker; any file in `src/crypto/testing/` must carry a sentinel; extend the "cannot" paragraph.

## LOW
- **P-16 —** manifest `device` and paths exclude only U+0000-001F and U+007F; C1 controls (U+009B is a terminal CSI) and bidi overrides pass and reach CLI output and notices — escape on output.
- **P-17 —** decrypt temp files hold plaintext in `.ipfs-sync/tmp/` until the next pull's sweep — sweep on plugin load and CLI start; list in the limits.
- **P-18 —** the plugin `rename` removes the target first (`obsidian-fs.ts`); crash between remove and rename loses the local file, recoverable only from a pinned root for the "replace" outcome; conflict copies are made first so it is data-safe for edits — note it.
- **P-19 —** how device B becomes an owner of the shared IPNS key for publishing (key adoption record) is not stated in second-device-publish — reference the existing adoption flow.
- **P-20 —** passphrase and slot dialogs may add "copy" controls: forbid or auto-clear the clipboard; notices that echo node-supplied text should be fixed strings (W-13 class).
- **P-21 —** the `previous.mtimes` size+mtime shortcut still trusts a file whose content changed with equal size and restored mtime — accepted limit; state it.
