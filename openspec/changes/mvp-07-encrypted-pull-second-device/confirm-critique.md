- **C-02 MAJOR — the fold-key algorithm contradicts its own required vectors; no source for full case folding.** D:131 and S:path-hardening:27 specify NFKC, then full case folding (CaseFolding.txt statuses C and F), then removal of default-ignorable code points. S:path-hardening:30-31 requires `.ıpfs-sync` (U+0131) to be skipped as `unsafe`; the vector list (T:27) also requires U+0130. CaseFolding.txt has no C or F entry for U+0131 (only the Turkic status T mapping, so unchanged); U+0130 folds under F to `i` + U+0307, and U+0307 is not default-ignorable, so it does not equal `.ipfs-sync`; JavaScript has no built-in full case folding. NTFS does alias U+0131 to `I` in its upcase table, which is the threat the vector covers. Fix: an explicit supplement to the fold (U+0131 to `i`, and strip a U+0307 that follows `i`), or define the fold as lower(upper(NFKC)) plus the ignorable strip; name the source of the folding table (a generated file checked in) and its unit test; put the table in 3.1's Files.

## The uncomfortable thing (critic)
The plan's strongest claim is that the release gate "binds the shipped bytes to the reviewed tree". That holds for the bytes; it does not hold for the judgement. The review record, the operator-run record and the timing acceptance are files in the operator's own account, written by the same agents that built the tree. The checker takes the lists of what must pass (assertion ids, checklist tests) from those same files. The git-history form only proves the record was not edited after the fact and accepts a fabricated record committed right after the last code commit. The first draft's flaw survives in a quieter form: Variant A is reachable (no blocking step found) but by a checker whose required lists the team can shorten. The likeliest real failure comes earlier: 07a's own task graph lets its gate run without the publisher deltas that make a second device safe, so real notes become reachable through a checker a person can satisfy by accident.
