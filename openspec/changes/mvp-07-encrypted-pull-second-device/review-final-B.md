## SECTION B1: PATH POLICY
VERDICT: PASS-WITH-FIXES. Critical 0, High 0, Medium 2, Low 4.

- **B1-01 MEDIUM** `src/sync/path-policy.ts:141-145` (`createPullExclusionMatcher`). For every segment the matcher rebuilds the prefix with `segments.slice(0, index+1).join("/")` even for unanchored rules: quadratic in depth. The decoder and `untrustedPathReason` cap only total path bytes (8 MiB) and entry count (100k), not depth or single-path length. An authenticated manifest with one path of about 1M segments reaches `evaluatePathPolicy` (`encrypted-pull.ts:475`) before any first-pull confirmation, and `adviseUnrestorablePaths` on every publish: about 10^12 character copies, so the main thread hangs. Trigger needs a vault-key holder (the threat model's "compromised device"). Fix: build the prefix incrementally or only for anchored rules; hard shape refusal at the top of `shapeRefusal` (e.g. path over 4096 bytes, segment over 255, more than 128 segments) and the same cap in the decoder; same pattern in the publisher's `createExclusionMatcher` (`exclusions.ts:70-77`), which now sees carried node paths. Owner ipfs-engineer.
- **B1-02 MEDIUM** `path-policy.ts:247-278` (`groupRefusal`/`groupRefusals`). Quadratic time and memory: `byKey` rebuilt with `[...(byKey.get(k) ?? []), path]`, `prefixGroups` rebuilt with `new Set([...prev, path])`, and `groupRefusal` copies and sorts the full member list for every member. Case variants of one 17-letter name give 131k paths with one fold key (above the 100k cap), or one file `a` plus 99,999 files `a/N`: about 10^11 comparisons, about 3 GB of arrays for a 20k group; pull OOMs or hangs before confirmation and before any blob request; the vault becomes un-publishable from devices that carry the entries. Not HIGH because the key holder can already wipe the manifest, but a cheap persistent DoS. Fix: one frozen group object per key, store only the first 3 names plus a count (spec already says at most three), mutable push arrays. Owner ipfs-engineer.
- **B1-03 LOW** `encrypted-manifest.ts:203-207,229-233`. The decoder calls `untrustedPathReason` via `checkPath`: one forged path with a control character, `..`, an absolute form, a backslash or lowercase `.ipfs-sync` makes the whole manifest fail to decode ("manifest-unsupported"). Spec scenarios say `../outside.md` is skipped with severity unsafe and the rest restored; in production the pull stops. The unsafe/shape skip, carry-forward drop and `needsAttention` paths for those inputs are reachable only from policy-level unit vectors. Fails closed (no bypass), but one bad entry makes the vault unpullable and unpublishable on every device and the message misleads. Fix: state in the spec that decoder strictness is intended, or make the policy the only gate for the pull while the decoder stays minimal for the publisher; verify 4.6b/6.1 through the production decode path. Owner product-manager (spec), ipfs-engineer.
- **B1-04 LOW** `cli/realpath-guard.ts:94-105`, `src/plugin/obsidian-fs.ts:165`. (a) The guard tests only "inside the vault root": a parent resolving to `<root>/.obsidian/plugins` or `<root>/.ipfs-sync` passes; with the stated swap race (directory swapped for a symlink to `.obsidian/plugins`, inside the root), the policy's folder protection is not re-applied at the filesystem layer (the prefix walk at commit time normally catches it). (b) The Obsidian adapter cannot see symlinks (spec accepts as residual): a desktop user's own symlinked folder gets pulled files written through it. Fix: (a) after `realpath`, refuse when the first segment of the real parent relative to the real root fold-matches `.obsidian`, `.ipfs-sync`, `.git` or the host config dir; (b) on desktop use Node `lstat`/`realpath` via the FileSystemAdapter base path, or restate as accepted residual. Owner ipfs-engineer.
- **B1-05 LOW** `path-policy.ts:79-104` (`escapeForDisplay`). Escapes C0, C1, U+061C, U+200E/F, U+2028/9, U+202A-E, U+2066-9 but not zero-width and format characters (U+200B-D, U+2060, U+FEFF, U+00AD, U+FE00-F, U+E0000 tags, other default-ignorables); bidi characters are escaped on display, not refused. A skipped path ".ob<U+200D>sidian/x" shows as ".obsidian/x" in notices and the reason says "plugin folder"; "invoice<U+202E>txt.exe" passes the policy and is written with a spoofed extension. Fix: also escape `DEFAULT_IGNORABLE_RANGES` plus Cf in display; decide whether bidi overrides are refused as unsafe/shape. Owner ipfs-engineer, product-manager decision.
- **B1-06 LOW** `tests/unit/path-fold.test.ts:199-219`. The check that the checked-in table equals the generator output from the pinned Unicode 17.0.0 files is `skipIf` unless `PATH_FOLD_UCD_DIR` is set; the default run proves only that the body matches its own recorded hash. A hand-edited table with an updated body hash passes CI. Fix: make the regeneration test mandatory in the phase gate and record `PATH_FOLD_UCD_DIR` in the gate commands. Owner ipfs-engineer, then bdd-engineer.

Per-area status (B1): realpath-guard retry CONFIRMED OK, no bypass (the retry result is returned to `assertParentInsideRoot`, which still applies `isInside(realRoot, realParent)` at line 104; dangling links still end in REFUSAL_DANGLING; the swap race remains exactly the stated residual; the retry does not widen it; a rare spurious refusal under a concurrent race fails closed). Node host writes OK. Write-time re-check OK (`commit()` runs `refusePath`, `findSymlink` incl. the final component, `needsCopy`/conflict copy, then rename). Plugin containment OK (`assertVaultPath` blocks NUL, backslash, leading "/", "."/".." segments; relies on upstream policy for drive letters and colons). Fold key and generated table OK (NFKC, table case fold, U+0131/U+0307 supplement, default-ignorable removal, up to 3 passes; vectors cover U+0131, U+0130, U+017F, U+212A, U+1E9E, fullwidth, ZWJ in .git, soft hyphen in .obsidian, NFC/NFD pair, a 2-pass vector; generator pins source sha256 and Unicode version, statuses C+F only, no timestamp). Collisions OK for correctness (performance B1-02). Pull-only exclusion matcher OK semantically (`.obsidian/` and `.smart-env/` fold-matched, nested `.obsidian` is expected; publisher matcher untouched by 07a beyond the list). Windows forms OK per spec (trailing dot/space and colon on the raw segment; reserved names on the fold key with the extension cut at the first dot; refused on every host; 8.3 rule; `abc~1.md` accepted; COM0 accepted per spec). Traversal, absolute paths, NUL/control OK in the policy (decoder stricter, B1-03). Severity classification matches spec. Carry-forward and exit codes consistent (`encrypted-pull-plan.ts:305-312,339`); minor inference: attack forms such as ".obsidian./plugins/x" and "OBSIDI~1/plugins/x" are classed platform, so they are carried and republished by victims; never written, so no direct harm.

## SECTION B2: CLI AND PLUGIN SURFACES
VERDICT: PASS-WITH-FIXES. Critical 0, High 0, Medium 3, Low 2.

- **B2-01 MEDIUM** `src/sync/pull-plan.ts:100-103,24-30`, `cli/pull-command.ts:208-211`, `src/plugin/pull-runner.ts:385-427`. The plaintext (v1) route does not use the new path policy: only `untrustedPathReason` and `excludedPathReason` (`toLowerCase`, case-sensitive, exact string). `evaluatePathPolicy` and `refusePath` are called only from the encrypted pull files. Whoever can write to the node can forge a v1 manifest; the reader is reached with `--allow-plaintext-v1` (CLI) or the plugin seam `allowPlaintextV1` on an unlatched destination. Plaintext targets ".obsıdian/plugins/p/main.js", ".obsidian./community-plugins.json", "OBSIDI~1/plugins/p/main.js", ".ob<ZWJ>sidian/..." pass; on NTFS they resolve to the real `.obsidian`; `assertVaultPullDestination` allows a vault whose only content is `.obsidian` (`pull-guard.ts:81`); a hostile node can drop and register plugin code (code execution after restart). "CON.md", "a:b" (alternate data stream) and case collisions are also unhandled. Help text claims "Paths under .obsidian/ are refused either way" (`help-text.ts:100-101`), false for alias forms. Mitigated by the opt-in flag and v1 removal in 07b. Fix: run `evaluatePathPolicy` and `refusePath` in v1 `planPull` and `pull-fetch`, or refuse the plaintext route outright in this release; correct the help text. Owner ipfs-engineer.
- **B2-02 MEDIUM** `cli/pull-command.ts:213-221`, `src/kubo/errors.ts:27-35`, `src/kubo/http.ts:76-83`, `src/plugin/pull-notices.ts:44-47`, `pull-runner.ts:180-191`. Node-supplied text reaches user output unescaped: `KuboHttpError.message` embeds the first `DETAIL_LIMIT` characters of the node's error body; the CLI prints `ipfs-sync: pull failed: ${error.message}` and the plugin shows the same in a Notice; `asStop` does not map KuboError to a fixed message. A hostile node/gateway answering HTTP 500 with ESC/C1/CSI sequences can overwrite earlier lines, inject titles or fake a "pull complete" line. The spec says notices that echo node-supplied text SHALL use fixed strings. Fix: wrap both sinks in `escapeForDisplay`, sanitise `detail` when `KuboHttpError` is built, or map KuboError to fixed text in `asStop`. Owner ipfs-engineer.
- **B2-03 MEDIUM** `src/plugin/request-url-transport.ts:29-41`, `src/sync/blob-source.ts:201-226`, `encrypted-pull-stage.ts:216`. The plugin transport buffers a whole response before any size check; the range probe tests only the smallest blob. A hostile gateway honours Range for the smallest blob, then answers the 22-byte header request of any larger blob with a full multi-GB body; `readUpTo` and the whole-body limit run only after `requestUrl` resolved the entire body; with up to 6 concurrent requests, mobile OOMs or crashes on every pull attempt. Code comments and task 6.2 already say the transport buffers; no mitigation beyond refusing afterwards. MEDIUM as DoS under a hostile gateway, not a confidentiality/integrity break. Fix options: streaming Node transport on desktop; cap in-flight header probes and probe every distinct size class; fail the pull after the first Range-ignoring answer; document the residual for mobile. Owner ipfs-engineer, documentation-specialist for wording.
- **B2-04 LOW** `src/plugin/pull-runner.ts:353-357,377-380`. `settle()` always calls `port.settle({ok:true})` in `finally` when `prompting` was set, so after a non-wrong stop (kdf-cost-refused, vault-mismatch, key-slots-invalid, slots-without-manifest) the unlock dialog is answered as success and closes, then the notice shows a stop. UX misreport only. Fix: pass `{ok:false, reason}` for stops. Owner ipfs-engineer/uiux-lead.
- **B2-05 LOW** `cli/pull-command.ts:113-120,138-139`. The v1 route prints manifest paths and failure reasons with no `escapeForDisplay`; `untrustedPathReason` rejects only C0 and DEL (`manifest-paths.ts:18`), so C1 characters such as U+009B reach `io.out`/`io.err`. Fix: escape in `printResult` and the `file.changed` handler (or fixed by B2-01). Owner ipfs-engineer.

Per-area status (B2): flag combinations OK (`--allow-rollback` only with `--root-cid`/`--manifest`; `--resolve-fork` only with a name target; the two together refused; `assertFlagsAllowed` before the first network call; `--allow-rollback` with a plaintext root refused after name resolution and probe requests, reads only; `--expect-vault-id` 32-hex regex; `--max-bytes`/`--expect-min-sequence` positive safe integers; `--passphrase` refused by name). First pull, large pull and fork prompts OK (no terminal and no flag is a stop with nothing written; a throwing callback counts as refusal; a declined large pull makes every writable path unfetched, exit 1). Encrypted-by-default routing OK (`--manifest-file` plaintext reader, `--root-cid` encrypted, otherwise the name's root decides via `rootIsEncrypted`; a gateway hiding both markers still hits `screenRoot`'s latch check; name resolved twice, a switch fails closed). Downgrade latch OK (`isLatched` counts `encrypted-seen.json`, `state/journal/keyslots.<16hex>.json`, abandoned backups). Passphrase sources and leakage OK (env var, 0600 file or prompt; asked after the destination is accepted; wiped in `finally`; events type-checked secret-free; `lastPull` summary has counts and CIDs only; plaintext auth secrets in data.json are pre-existing). Exit codes OK. Session keys OK (the pull never unlocks the session; `session.provider()` bypasses derivation only when `sameBytes(unlocked.keySlots, bytes)` and `assertHeldVaultApplies` hold; the record/floor check, the destination marker guard and the cost question remain; the first pull cannot run unattended). Restore OK (labels marked unchecked unless the entry authenticates with an agreeing sequence; chosen entry re-authenticated before the dialog; mismatch refused before the dialog; rollback flag only from `restore` after confirmation). Dialogs OK (values via `text`/`setText`, no HTML). `settleUnlock` no auth or secret issue (see B2-04). Load-time behaviour OK (`onload` awaits only settings load and a local key-slot refresh; catch-up and the temp sweep deferred to `onLayoutReady`, sweep is try-acquire only).
