# Review 6.4, pass A: sync core, read side (security-reviewer)

Reviewer: security-reviewer. Static read only; nothing executed; cross-model judge not run (single-reviewer read). Saved by the lead as a condensed record (2026-10-03). To be merged into review-final.md.

VERDICT: PASS-WITH-FIXES. Critical 0, High 0, Medium 2, Low 6. No way found for a hostile node to make the pull side accept forged, replayed-below-the-record or truncated data, or to write outside the temp, destination or conflict-copy paths. Both Mediums are on the publish side.

## Findings
- **A-01 MEDIUM** `src/sync/publish.ts:296-311`, `publish-commit.ts:153-154`. The sequence decision (`assessNode` reads `manifest.enc`, `nextSequence` at 296) is made long before `recordNameStart` (308) and `commitPublish` overwrites `manifest.enc` without comparing `previous.sequence` with `manifest.sequence`. Scenario: device B publishes sequence N while A is planning (minutes on a big vault or mobile); A's start reading already returns B's root; A overwrites B's `manifest.enc` with its own sequence N; the recheck passes (start equals end); A publishes its own sequence-N root. Two sequence-N manifests exist and B's publication is displaced; if A had not seen B's device, the stray drift guard can delete B's blobs from `current/`. Recoverable through `pull --resolve-fork`, but silent on A. Docs say the window is "between the second read and name/publish"; the real window starts at the first `manifest.enc` read. Fix: in `commitPublish`, after reading `previous`, decode it; if it authenticates with `sequence >= manifest.sequence` and an identity other than this publish's, throw `overlappingPublish` before any write; move `recordNameStart` before `assessNode` (or re-read name and `manifest.enc` just before `transfer`). Owners: identity-security-engineer (publish-commit, name-recheck), ipfs-engineer (publish.ts ordering).
- **A-02 MEDIUM** `publish.ts:71-76`, `publish-sequence.ts:52-63`, `sequence-rules.ts:27`, `vault-keys.ts:217-223`, `repair.ts:97`. Publish never consults the sequence floor to refuse a restart from sequence 1 or to choose the next sequence; only `--repair` "ahead" reads it. Scenario: device's state file is lost but the key-slot copy remains and the floor says sequence 40; a hostile or wiped node shows no `manifest.enc`; `openVault` takes `resumeOrLost` (origin resumed-creation); `classifySequence(undefined, undefined)` returns `first-publish`; the device publishes sequence 1 under the owned name with no flag; every other device holding the floor refuses it as older; the vault is stuck until the floor is deleted by hand. Related: repair "behind"/"rebuild" compute `max(local, node, record) + 1` without the floor and can land below it after a pull crash window. Fix: read the floor for `opened.vaultId` on every publish; if an entry exists and local state is missing or `state.sequence < floor.sequence`, refuse first-publish, resumed-creation and rebuild with a "pull first" message; take `max(..., floor.sequence) + 1` in `planRepair`; add the requirement to the second-device-publish spec. Owner: identity-security-engineer.
- **A-03 LOW** `publish-commit.ts:153,161,174-180`. `withdrawManifestFile` trusts a node-served `previous` and is not atomic. Only authenticated bytes can be written (AES-GCM envelope under the vault key, same `vaultId`, `sequence >= manifest.sequence`, current file still equals the bytes this publish wrote); a hostile node can supply any genuine past manifest of this vault at or above our sequence, landing a stale genuine `manifest.enc` in the mutable MFS tree only (pullers read the immutable root; no pull-side rollback). Residual: `previous` is never matched to the root the name now points at; the `now` read and write are two calls (a third publisher's manifest in between is clobbered); a failing `writeManifestFile` replaces the original `overlapping-publish` refusal (line 161). Fix: restore only when `previous` is byte-equal to the `manifest.enc` inside the root the failed recheck resolved; catch errors from `withdrawManifestFile` and rethrow the original refusal. Owner: identity-security-engineer.
- **A-04 LOW** `name-recheck.ts:22-33,44-46`, `src/kubo/ipns.ts:77-87`. On a non-first publish, `not-found` at the start is accepted as a "no record" baseline; the `ipns.ts` observation (timeout and not-found return the same text, timeout table empty) means a real timeout classifies as not-found. Scenario: state has `rootCid != null`, both reads return not-found from a flaky resolver; the overlap check passes vacuously (a hostile node can always do this; limited to the honest-race case). Fix: when local state has a non-null `rootCid` and the key was not created in this run, treat not-found as failed and refuse. Owner: identity-security-engineer.
- **A-05 LOW** `encrypted-pull-fetch.ts:226-233`, `pull-conflict.ts:59-71`. No re-check of the local file between the conflict-copy read and the final rename: an edit saved by the user or another plugin after `copyToTemp` and before `rename(temp, path)` is in neither the copy nor the vault. Fix: re-stat size and mtime after the copy and before the rename; redo the copy or return unfetched. Owner: ipfs-engineer.
- **A-06 LOW** `encrypted-pull-stage.ts:279-289`, `diff.ts:112`. A restore that writes an `unmaterialized` path leaves it in `unmaterialized` (`restoredState` keeps `...state`); the next publish carries the node's entry and never reads the local file, so restored content is not published (breaks "publish after restore contains restored contents" for those paths; nothing lost: the next pull keeps the local file as a conflict copy). Fix: remove restore-written paths from `unmaterialized`, or state the exception in the spec and restore output. Owner: ipfs-engineer.
- **A-07 LOW** `encrypted-pull.ts:522-531`. The pull takes `publish.lock` without the post-acquire token verification publish has (`withTokenCheck` is used only in `publish-runner.ts:259` and `publish-command.ts:207`); the plugin temp sweep (`pull-sweep.ts`) has the same gap. On an adapter whose rename can replace an existing lock file, two starters taking over a stale lock both believe they hold it until the first heartbeat (60 s). Fix: wrap the lock file in `withTokenCheck` in the pull and the sweep; call `verifyHeld` before `authorize`'s first write. Owners: ipfs-engineer, identity-security-engineer.
- **A-08 LOW** `sequence-floor.ts:144-150`, `cli/device-store-node.ts:111-134`. `raiseFloor` is read, merge, write with no inter-process lock: two CLI processes pulling different vaults can drop each other's raise (last rename wins), weakening anti-rollback for that vault until its next raise. Fix: exclusive lock file in the device-store directory around the read-merge-write, or re-read after rename and re-merge. Owner: identity-security-engineer.

## Per-area status
Unlock for pull OK (cost policy m ≤ 128 MiB, t ≤ 4, p = 1; floor and `--expect-vault-id` checked before derivation; key-slot copy stored only after manifest authenticates). Pull verdicts and floor OK (rollback by name refused; older by `--root-cid`/`--manifest` needs `--allow-rollback`; a fork is never resolved by that flag; floor raised in `authorize` before any file or state write; residual A-08; the floor keeps at most 64 vaults). Blob fetch and verify OK (blobs only from `/ipfs/<manifest.rootCID>/…`; lying lengths, truncation, extra bytes refused; part files removed on every failure path; the sweep lists only `.ipfs-sync/tmp/` regular files matching `^[0-9A-Za-z-]+\.(part|copy)$`, so no hostile name can make it delete a non-temp file). Baseline merge, unmaterialized, carry-forward OK except A-06. Restore and fork resolution OK (ancestor only when exactly one authenticated entry matches `previousIdentity`; a hostile node can only withhold or duplicate entries, which means no ancestor and conflict copies). Locks and token hook mostly OK (`beforeFirstWrite` awaited in `publish-session.ts:145`, `history-gate.ts:17`, `publish.ts:166`; residual A-07). Name recheck, journal start root, resume, commit: findings A-01, A-03, A-04; latent API risk: `PendingPublish.nameStart` is optional and omitting it silently disables the end re-check (all production callers pass it). Publisher deltas OK except A-02 (`.smart-env/` unanchored like `.git/`; previously published `.smart-env` blobs remain encrypted in older roots).

## Could not verify
Atomicity and containment of host `rename`/`append`/`remove`, `HostPathError` behaviour, the symlink-swap race between `findSymlink` and `rename`; real kubo behaviour (`files/write` under concurrent writers, `ls` size claims, `name/resolve` timeout text, whether the gateway verifies CIDs: the client does not); whether the plugin lock-file adapter's rename can replace an existing file (basis of A-07's severity); crypto internals beyond `blob.ts`, `argon2.ts` and the top of `key-slots.ts` (`prepareTriedSlots` count cap, `parseKeySlots` caps, `manifest-envelope`, constant-time claims); `pull-restore.ts`, `pull.ts` (v1 dispatcher), the Windows branch of the device store; runtime memory under hostile gateways in the plugin (`requestUrl` buffers whole bodies); whether tests cover the crash-timing windows named.
