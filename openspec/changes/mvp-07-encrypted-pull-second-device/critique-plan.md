# Plan critique — mvp-07 artifact set (artifact-critic, independent)

Reviewer: artifact-critic. Static read of every mvp-07 artifact and the referenced code; ran nothing; no access to how the plan was produced. Saved by the lead as a condensed record (2026-09-30); every finding id, location and fix is kept, narratives shortened. Notation: T = tasks.md, D = design.md, P = proposal.md, S:<name> = specs/<name>/spec.md.

VERDICT: NOT READY. Several tasks cannot be executed as written and the headline outcome (Variant A, guard removed) is unreachable by the plan's own checker. Fix F-01..F-04 first (each is a design decision), then F-05, F-06, F-07, F-09, F-10, F-11 (wrong claims about the code or task-order errors), then re-issue.

## BLOCKERS
- **F-01 — Variant A can never be selected, because task 6.3 changes code the review hash covers.** T:40 (6.3) replaces the two guard modules and also removes the exported fixture-only check from the shared configuration; D:73 hashes all of `src/` and `cli/` except the two guard modules; D:82 selects Variant A only if the checker exits 0 after removal. The policy lives outside the two modules: `src/core/config/node-safety.ts:133-162` (`assertFixtureVault`, `markerProblem`, `MARK_FIXTURE_HINT`, the "not yet independently reviewed" text at line 161), `src/core/config/defaults.ts:10,13` (marker values), `src/plugin/publish-notices.ts:17` (review-pending notice), `tools/webview-probe-entry.ts:3` and `tools/webview-probe-kubo-core-entry.ts:1` (import `assertFixtureVault`). Consequences: editing `src/core/config` after review changes the tree hash so checkers A and B fail and the release is forced to Variant B; removing the export breaks the WebView probe that 6.3 must pass; existing guard tests assert refusal and must change, conflicting with "change nothing else"; 2.1's verify ("marker values and review-pending message only in the two guard modules") fails on today's tree. Fix: 2.1 moves ALL policy into the two modules (`assertFixtureVault`, marker constants, hints, notice text); config keeps no fixture-only export; the permissive replacement keeps the export names; name the tests and probe entries that change at 6.3, or update them in 2.1 so they need no edit later.
- **F-02 — the post-removal guard content is never stored, and a permissive no-op drops a safety check.** T:34 (5.2) and D:73-76 record only hashes of the post-removal content; 6.3 says "exactly the content the review recorded" but no file holds it; D:71 defines the replacement as "permissive no-ops". `src/sync/pull-guard.ts:34-35` and `:76-77` call `findSymlink(fs, TEMP_DIR)`, which stops pull writing state and temp files through a symlink — unrelated to marker policy, silently removed by a wholesale no-op. Fix: save the proposed modules as files under the change directory (e.g. `guard-after-removal/*.ts`) before review; the checker hashes those files; 6.3 copies them byte for byte; split the symlink/state-folder guard out of the policy modules so it survives removal.
- **F-03 — "restore and record" contradicts the state model; the "next publish republishes" scenario cannot occur.** S:rollback-detection:44 says the record "SHALL describe the restored manifest so that the next publish sees the difference"; D:37 says the record keeps the highest `sequence` while restoring. `src/sync/root-state.ts:57,59` makes `decodeRootState` throw unless `sequence === manifest.sequence` and `vaultId === manifest.vaultId`; `src/sync/sequence-rules.ts:31` treats equal sequence with different `rootCID` as `fork`, which `--repair` cannot lift (`repair.ts:66-67`). If the record describes the restored (sequence-2) content, local files equal the record and publish sees no difference (the scenario at S:rollback-detection:54-56 never happens); if it keeps sequence 5, decode throws; if it holds the sequence-2 manifest at sequence 5, publish reports an unrepairable fork. Fix: add a separate `highestSequence` field distinct from `sequence`; restore leaves `manifest` at the node's current sequence-5 manifest so local files differ and publish sees the change (the v1 pull mechanism, `pull.ts:266-269`); rewrite the requirement; add a scenario test in 2.2/2.3.
- **F-04 — "prune oldest" and "last 20 history entries" have no ordering source.** T:16 (2.7), S:history-pruning:8, T:21 (3.1), D:140 (Open Question 12). History files are named `<currentCID>.enc` (`history-check.ts:20`, regex `^[A-Za-z0-9]{10,128}\.enc$`); `files/ls` returns names, CIDs, types only; the sequence is inside the encrypted manifest. "Oldest 1,500 of 1,600" cannot be computed without decrypting all 1,600 files (each up to 64 MiB); "refuse unless the newest manifest authenticates" has no definition of newest; the 2.7 test is unwritable and the plugin's "last 20" list is unimplementable. Fix: choose an ordering in the design (decrypt-and-sort with a byte budget, a local sequence-to-CID index written at publish time, or a change to the mvp-06 name format), not an open question.

- **F-12 — the plugin cannot stream, so the memory claims are false for the plugin.** D:56, S:encrypted-pull:74-76 (100 MB file holds at most one plaintext and one ciphertext segment), T:12 verify ("never more than two segments"). `request-url-transport.ts:10-14,41` says "The body arrives whole (no streaming)"; D:32 fetches whole blobs with `stream /ipfs/<root>/<blob>`; `gatewayStream` supports ranges (`gateway.ts:78`, `GatewayRange`). - **F-15 — a rewrap leaves it unstated whether the old slot stays in the new `keyslots.json`.** D:59-60, T:5 ("the old slot still opens the key"), S:key-management:8; `KEY_SLOTS_MAX_SLOTS = 8`, `KEY_SLOTS_MAX_TRIED = 2` (`key-slot-format.ts:29,31`). - **F-16 — restoring across a rewrap is impossible, and the accept action can downgrade the local slot copy.** D:29, D:61, S:encrypted-pull:112-121, S:key-management:51-64. Fix: for `--root-cid`/`--manifest`, unlock and verify the local copy against the target manifest instead of comparing bytes, or define restore-across-rewrap explicitly; accept must not lower cost silently.

## The uncomfortable thing (critic)
The plan's safety story is that the guard comes off only when a tool checks three pieces of evidence, each a text or JSON file the same team writes, read by a tool that trusts self-declared fields; the hash tying them together excludes the build inputs; the only evidence that touches real behaviour (the Obsidian run) happens after the cadence freeze, and a bug found there invalidates the review and the run. F-01 shows the design is not self-consistent about which code the review covers: the config change at 6.3 alone forces Variant B. The likeliest outcome is someone editing the checker or the tree at 6.3 to reach Variant A — the moment real notes become reachable, with the reviewed-vs-shipped gap the plan set out to close.
