The feature operations proved the harness shape against the live node: `tools/feature-op-mvp-07a/` contributes the loopback forwarding proxy (`proxy.mjs: createProxy({ upstream, demoRoot })`), the request allowlist policy (`policy.mjs`), the per-device CLI child runner with scrubbed environment and effective-target assertion (`children.mjs`), and the reporting/self-test machinery; `tools/feature-op-mvp-08.mjs` shows the import-not-copy reuse pattern and adds the per-device `XDG_STATE_HOME` discipline that keeps the PGlite history database (`<state>/ipfs-sync/history`) out of the operator's real state directory. The tampered-segment exercise comes from `tools/feature-op-mvp-07/hostile-tools.mjs` (`prepare-tamper`: reads a genuine root, flips one bit in one blob past the 22-byte header, writes a new authentic `manifest.enc` at a higher sequence — built with the vault's own passphrase through the test-only unwrap hook — all confined to `<root>/tamper`, then pulled with `--root-cid`, per `tools/feature-op-mvp-07/hostile-phase.mjs:30-40`).

Facts verified while authoring this change (read, not assumed):

- `vitest.config.ts:10` includes `tests/**/*.test.ts`. A spec named `*.e2e.ts` does not match `*.test.ts`, so the default gate never discovers the suite and `vitest.config.ts` needs no edit.

- The 07a policy and runner modules hardcode `KEY = "obsidian-vault-sync"` and `DEMO_PARENT` (`tools/feature-op-mvp-07a/constants.mjs:14-15`; used at `policy.mjs:105-110` and `children.mjs:6,40,57`). They cannot be reused as-is for a different key, and scope forbids editing `tools/`.

Against the real network, this suite's budgets are larger (decision 7).

Tamper assertions are ported from `tools/feature-op-mvp-07a/hostile-phase.mjs:107-119`: exit 1, `integrity-failed <path>` on stderr, that file absent, no `.ipfs-sync/tmp/` leftovers, every other file fetched, no mutations besides the preparer's.

## Goals / Non-Goals

**Goals:**
- `pnpm test:e2e` runs the encrypted loop — publish → resolve → pull → conflict, wrong passphrase, tampered segment — as child processes of the real built CLI against ipfs.prometheusags.ai, and exits 0.
- Every run is confined: its own `/obsidian-vault-sync/e2e-<runId>/` root, the suite-owned key `obsidian-vault-e2e`, a loopback proxy that refuses anything outside the allowlist, per-device state directories in a per-run temp dir outside the repository.
- Cleanup is automatic and total: the run removes exactly its own root on success, on failure and best-effort on signal; the last scenario proves `files/ls /obsidian-vault-sync` holds no `e2e-` entries.
- The default gate `pnpm test` stays fully offline and never discovers the suite.
- The mvp-08 history recorder is proven in the loop: one assertion that a fresh CLI process reads the run's operations from the on-disk database in the per-run state dir.

**Non-Goals:**
- No edits to `src/`, `cli/`, `tools/`, root `vitest.config.ts`, `playwright.config.ts` or CI (`.github/` is release-deployment-lead's; the skip/fail decision below is recorded so a later CI change can adopt it without re-deciding).
- No retirement of `tools/feature-op-mvp-*.mjs`. They remain the operator/demo harnesses; the suite replaces the unevidenced bring-up claim (assess WARNING 3), not the tools.
- No plugin-surface E2E (the in-Obsidian proof is the release demos of mvp-05/07/10).
- No multi-vault, large-file, range-read or mobile coverage (carried on the 07a unverified list).
- No `--local-stub` mode: v1 always talks to the real node through the proxy (fewer moving parts; the stub stays tool-only).

## Decisions

1. **Suite shape.** All e2e code lives under `tests/e2e/`: `vitest.config.ts` (extends the root config; `root` set to the repository; `include: ["tests/e2e/**/*.e2e.ts"]`; hook and test timeouts per decision 7; serial execution), `harness/` modules (run context, proxy, policy, child runner, node view), one ordered spec file `encrypted-loop.e2e.ts` holding every scenario as sequential `it` blocks, and `README.md` (run instructions). A single spec file with `beforeAll`/`afterAll` owning the run lifecycle is chosen over multiple files because vitest runs files in parallel by default and the scenarios share one run root, one proxy and two devices — ordering must be by construction, not convention. The `.e2e.ts` suffix keeps the files out of the default gate's include pattern (verified above); no root-config edit.
2. **Run identity and the suite-owned key.** `runId` matches `/^[a-z0-9-]{8,}$/` (the 07a `RUN_ID_PATTERN`); the run root is `/obsidian-vault-sync/e2e-<runId>` — directly under the base, per the phase plan, unlike the feature ops' per-change demo parents. The key `obsidian-vault-e2e` is created with `key/gen` only when absent; when present, its key ID must be recorded in the per-machine owned-keys config (the same `assertKeyAdoptable` rule as 07a, importing `readOwnedKeys`/`ensureConfig` from `tools/feature-op-mvp-07a/workspace.mjs`) or passed explicitly, or the suite refuses. The key persists across runs and is never removed. Rejected alternative — a per-run key (`obsidian-vault-e2e-<runId>` matches the pattern too): `key/rm` is forbidden project-wide, so keys would accumulate on the shared node without bound. Consequence accepted and recorded: one suite key means two concurrent suite runs (across machines; a per-machine lock file in tmpdir prevents it locally, 07a `acquireLock` pattern) can interleave `name/publish`. The MFS roots never collide (per-run roots), and every pull carries `--expect-vault-id`, so a repoint race fails closed with a refusal, never wrong data.
3. **Reuse vs. re-declare (the tools boundary).** Scope is `tests/` only, so nothing in `tools/` is edited. Reused by import (key-agnostic, verified so by reading): `isWithin`, `isValidRunId`, `newRunId`, `childEnv`, redaction/scrub helpers from `tools/feature-op-mvp-07a/policy.mjs`; `ensureConfig`, `readOwnedKeys`, `assertKeyAdoptable`, `acquireLock`, vault generation/walk helpers from `tools/feature-op-mvp-07a/workspace.mjs`; `startStub` is NOT imported (no stub mode); the `prepare-tamper` op is invoked through the existing `runHostile` entry of `tools/feature-op-mvp-07/` (root-scoped and key-free — it writes only `files/write`/`files/mkdir` below the given `tamperDir`, `hostile-tools.mjs:5-6,78-87`). Re-declared in `tests/e2e/` because they are bound to the feature ops' key or demo roots: the proxy and its allowlist policy (07a hardcodes `obsidian-vault-sync`), the child runner's argv shape (`--key obsidian-vault-e2e`), the run/cleanup lifecycle. The suite's policy permits exactly: `files/write|mkdir|rm|stat|ls` at or below the run root, `key/gen` of `obsidian-vault-e2e` only, `key/list`, `name/resolve`, `name/publish` with `key=obsidian-vault-e2e` of a CID the node reported under the run root, `pin/add`, `ls`/`cat`-style reads of `/ipfs/<cid>`, and gateway GET/HEAD — and refuses `key/rm`, `key/rename`, `key/import`, `key/export`, `pin/rm`, `files/mv`, `files/cp`, any path outside the run root (including a sibling `e2e-<other>` root), anything naming `/obsidian-vault-staging`, and any other key name (including `obsidian-vault-sync`). The policy is a pure function and gets offline unit tests in the default gate (`tests/unit/e2e-proxy-policy.test.ts`), so the confinement matrix is gated without the node.
4. **Child isolation.** Every scenario step is a spawned child of `dist/cli/ipfs-sync.mjs` (never library calls for the sync loop; the only `src/` import anywhere in the suite is the test-only unwrap hook, used by the tamper preparer). Each simulated device gets its own vault directory, config file and per-user state directory (`XDG_STATE_HOME` and `HOME` both pointed at the per-run temp dir, absolute and outside the repository — the runner refuses otherwise, 07a `children.mjs:48-49` pattern). Child environments are the 07a allowlist (`PATH, HOME, TMPDIR, LANG, LC_ALL`, plus the `IPFS_SYNC_*` auth variables on the shared-node path only), so the operator's real device id, sequence floor and history database are never read or written, and the mvp-08 recorder writes under the per-run state. Before every spawn the effective configuration is computed with the CLI's own config loader from the exact argv/env and must equal the loopback proxy, a root inside the run root and the e2e key (the `assertEffectiveTarget` pattern, re-bound). Passphrases are generated per run, live in a 0600 file in a 0700 per-run directory outside the repo, and every child's output is scanned for both spellings before printing (the 07a scrub discipline).
5. **Preflights: fail fast, never skip.** Before the first scenario the suite refuses (exit nonzero, named reason) when: (a) `process.version` does not satisfy `engines.node` >= 24.15.0 — the message names the fix (`PATH=/opt/homebrew/bin:$PATH pnpm test:e2e` on this machine; default shell node is 24.11.1, mvp-08 gate note) — (b) `dist/cli/ipfs-sync.mjs` is missing or older than `cli/` or `src/` (the suite never builds; 07a `checkBuildFresh` pattern), or (c) the node does not answer a bounded read-only probe (`version` plus `key/list` through the upstream, then the proxy self-test against a dead loopback upstream proving refusals are not forwarded). **Recorded decision on unreachable node: the suite FAILS loudly.** It never skips: the command is already explicit opt-in, the suite's purpose is goal-6 evidence, and a green-with-skip summary is indistinguishable from a pass in CI logs. The default gate excludes the suite entirely (decision 1), so offline developers are never touched. CI wiring is out of scope; this decision is what a future CI change adopts.
6. **Cleanup semantics — success, failure and signal.** The last scenario, S5, performs the cleanup itself as a normal ordered step: `files/rm -r` of exactly the run root (bounded retries, `files/stat` before and after), then re-lists `/obsidian-vault-sync` and asserts no `e2e-` prefixed entries. This keeps cleanup and its proof in the deterministic scenario order instead of depending on vitest hook-ordering subtleties. The `afterAll` is the safety net for the failure path: whether scenarios passed, failed or never ran, it attempts the same removal (idempotent — an already-removed root is detected by `files/stat` and skipped), and a cleanup failure there fails the suite naming the root. `SIGINT`/`SIGTERM`/`SIGHUP` trigger a bounded best-effort cleanup before exit (the 07a `SIGNAL_POST_RUN_TIMEOUT_MS = 5000` precedent, `constants.mjs:32`). The suite never removes anything else: no other run's root, no pin, no key — automatic removal is confined to the run's own root by the proxy policy (decision 3), not by convention. A stale root from a previously crashed run fails S5's listing loudly and prints the exact operator removal command for that specific root. Rationale for not auto-removing stale roots: "cleans up only its own root" (phase plan) — a run cannot distinguish a crashed sibling's root from one being written right now.
7. **Timeouts from measured costs.** Per-scenario `it` timeout 240_000 ms; `beforeAll`/`afterAll` hook timeout 300_000 ms; per-child spawn timeout 300_000 ms (the 07a `CHILD_TIMEOUT_MS`). Basis: ~1.8 s PGlite boot per spawn (mvp-08 measurement), 32 s for the heaviest all-local CLI scenario (mvp-07 measurement), plus real-network latency and Argon2id unlocks per pull; 240 s is roughly 7x the heaviest local scenario. The suite-wide vitest `testTimeout` default (20 s) is overridden only in `tests/e2e/vitest.config.ts`.
8. **Scenario set and order** (one file, sequential): S1 *publish → resolve → pull*: device A generates a fixture vault, `init --passphrase-file`, `publish` (sequence 1); `name/resolve` of `obsidian-vault-e2e` returns the published root; empty device B pulls with `--accept-first-pull --expect-vault-id --expect-min-sequence 1`; contents match A and the proxy's plaintext needle scan is empty. S2 *conflict*: B edits one shared note locally (no publish), A edits the same note and publishes (sequence 2); `name/resolve` returns the new root; B pulls — remote content wins, B's local edit survives as `<stem> (ipfs conflict YYYY-MM-DD).md` next to it, no local file is deleted, untouched files are not rewritten; then the single history assertion: a fresh CLI child runs `ipfs-sync history` against B's state directory and lists the pull (conflicted >= 1) and the conflict record, proving the mvp-08 recorder wrote to the per-run on-disk database (one assertion — `--limit` ordering and plaintext greps are mvp-08's gate, not re-tested here). S3 *wrong passphrase*: fresh device C pulls with a different generated passphrase — nonzero exit, stderr names the unlock failure (`wrong passphrase or damaged key slot`), and C's vault holds no pulled file, no `.ipfs-sync` state, no sequence floor. S4 *tampered segment*: the `prepare-tamper` op, in its complete-tree mode (spec delta 2026-10-06 below), writes a FULL copy of the genuine tree under `<runRoot>/tamper` with exactly one blob's bit flipped and a new authentic `manifest.enc` at a higher sequence (every write a `files/write`/`files/mkdir` inside it, audited); a FRESH device pulls the tampered root with `--root-cid` — exit 1, `integrity-failed <path>` on stderr, that file absent, every other file fetched (counts N-1 fetched, 0 unchanged, 0 conflicts, 1 integrity-failed), no `.ipfs-sync/tmp/` leftovers, and the proxy log shows no mutation besides the preparer's confined writes. S5 *cleanup and no leftovers*: decision 6 — the scenario removes the run root and then proves `files/ls /obsidian-vault-sync` holds no `e2e-` entries.
9. **No result-document ceremony.** The feature ops write JSON result documents with pre/post IPNS pointer restore instructions because they move the operator demo key. The suite's evidence is the vitest report itself (stdout, exit code); the e2e key has no restore story (it is disposable and suite-owned). What is kept from the ceremony: the per-machine lock, the build-freshness refusal, the proxy self-test, the needle scan, the signal cleanup.

## Spec delta — 2026-10-06 (S4 / task 2.4 mechanism)

**Conflict found.** Task 2.4 as originally written merged two incompatible things: the 07a stub-corruption outcome assertions ("every other file fetched") and the 07 `prepare-tamper` mechanism, which writes only the flipped blob into the tamper tree and points the manifest's rootCID at that incomplete tree. Under that mechanism the outcome assertions are unsatisfiable.

**Live evidence.** A fresh device pulling that root reported all 11 fixture files integrity-failed and 0 fetched. Cause: the pull fetches exclusively from the tree the manifest names (`src/sync/encrypted-pull-stage.ts:210-213`, `src/sync/encrypted-pull-fetch.ts:60-104` — a blob the named tree does not list fails the file as a fetch/integrity error), so every blob missing from the incomplete tamper tree fails, not just the flipped one.

**Resolution (lead decision; grounded in the plan's intent, `.kbd-orchestrator/phases/mvp/plan.md:146` — "that file fail with an integrity error while the other files sync").** The preparer gains a complete-tree mode: every blob of the genuine tree is copied into `<runRoot>/tamper`, with exactly one blob flipped. A fresh device pulling the tampered root then fetches every intact file and fails only the tampered one: exit 1, `integrity-failed <path>` on stderr, that file absent, counts N-1 fetched / 0 unchanged / 0 conflicts / 1 integrity-failed, no `.ipfs-sync/tmp/` leftovers, preparer writes confined to `<runRoot>/tamper`. Decision 8's S4 text, task 2.4 and the S4 spec requirement are amended accordingly.

## Risks / Trade-offs

- [The suite mutates a shared node on every run] -> mitigated structurally: proxy allowlist (decision 3) confines mutations to the run root and the suite key, the policy is unit-tested offline, and cleanup plus the no-leftovers gate make each run self-erasing. The residual risk — a crashed run leaves one `e2e-<runId>` root — is surfaced by S5 at the next run with the exact removal command.
- [One permanent suite key accumulates IPNS history and can be repointed by a concurrent run] -> accepted and recorded (decision 2): per-run keys are worse (no `key/rm` ever, unbounded keystore growth); pulls carry `--expect-vault-id` so a race fails closed.
- [Fail-not-skip makes `pnpm test:e2e` red when the node is down] -> deliberate (decision 5): the command is opt-in and its red means "no evidence today", which is the truth. The offline gate never runs it.
- [Re-declaring the proxy/policy in tests/ duplicates 07a logic] -> accepted: scope forbids editing `tools/`, and the duplicate is the version bound to the e2e key; the policy's behavior is pinned by the offline unit tests so drift is caught. If a later change generalizes the 07a modules to take a key parameter, the suite should adopt them (recorded here, not tasked).
- [Live-node runs are slower and flakier than the stub] -> timeouts sized from measurements (decision 7); the tamper scenario's preparer writes only inside the run root so the hostile object never touches another project. No retry loop on scenario assertions: a flake fails the run and the reason is printed (the flake-budget question is deferred to CI adoption, which is out of scope).
- [The passphrase file and needle scans are test-only secrets handling] -> same discipline as 07a/08: 0600/0700 per-run directory outside the repo, wiped at run end, output scanned for both spellings before printing.

## Migration Plan

Nothing to migrate: no prior suite, no config change, no production code. Rollback is `git revert` of the change (tests and the script line). If a run of the suite has ever executed on a machine, the shared node holds the permanent `obsidian-vault-e2e` key and possibly one stale `e2e-<runId>` root; the key stays (key/rm is forbidden project-wide; it is inert), and a stale root is removed by the operator with `files/rm -r` of that exact path — the S5 failure message prints it.

## Feature Operation

The final task's gate is a real run, from a fresh `pnpm build`:

```
PATH=/opt/homebrew/bin:$PATH pnpm test:e2e
```

against ipfs.prometheusags.ai (the operator's `IPFS_SYNC_RPC_URL`/`IPFS_SYNC_GATEWAY_URL` and auth variables supply the node; the suite hardcodes no address). Exit 0, the vitest output pasted into the execution record, and afterwards a read-only `files/ls` of `/obsidian-vault-sync` (via the CLI toolbox or `curl` with query-string args per the node-quirks constraint) shows no `e2e-` entries — pasted next to the run output. Report what stays unverified: concurrent-run behavior across machines (the per-machine lock and `--expect-vault-id` are the mitigation), large-file and range-read pulls, an authenticated endpoint, non-macOS hosts, and plugin-surface sync (release demos own it).
