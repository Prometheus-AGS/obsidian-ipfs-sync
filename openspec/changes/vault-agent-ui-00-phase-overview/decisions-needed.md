## D1. React 19, shadcn/ui and assistant-ui for chat: DECIDED

Decision (operator, 2026-10-04, relayed by the lead): the Vault agent UI uses React 19, shadcn/ui and assistant-ui for chat, "so we get the absolute best UI/UX". The lead's native-DOM recommendation is withdrawn. `vault-agent-ui` builds on the `chat-react-shell` stack and plan; it does not supersede it wholesale.

Stack as recorded in `chat-00-phase-overview/README.md` (operator decisions 2026-10-02, agent-read pins 2026-10-02, re-verify at pin time): React 19.3.0, vanilla zustand stores, `@prometheus-ags/prometheus-entity-management` 4.0.2, assistant-ui with our own external-store runtime adapter (no `@assistant-ui/react-ag-ui`), shadcn on Base UI, the chat-01 device spike gate, lazy evaluation inside `main.js`, the layering rule (components, hooks, stores, services). None of the pins is in `versions.toml` (checked: it holds `@noble/hashes`, `typescript`, `node`). Agents cannot edit that file; `tasks.md` 0.5 is the operator's.

What D1 does not decide: conversation persistence as entities (chat-00 decision 3) waits on D15; whether PEM's React barrel or core plus thin hooks (chat-00 open item 1, chat-02 1.6); the Tailwind variant (chat-01 S3 result); G1 itself.

Conflict: control center Revoke copy ("loses sync access when its current grant expires. ## D9. Lane taxonomy and per-turn lane field

Conflict: spec 005 lanes are `local-onnx`, `local-webllm`, `remote-agui` (and `remote-a2a`) with fallback chains; spec 009 says "offline, local-only badge"; the chip has Local, Remote, Offline where Offline is connectivity. Screens disagree on chip text and put detail in a `title` tooltip (`rag-chat.html:136`, checked), invisible on touch.
Recommended: the chip names the lane that produced this turn (Local or Remote) plus a connectivity suffix when offline; detail is visible text. With slice 02, a provider declares its locality: `Local` only for a loopback host or an in-process lane, otherwise `Remote`. A desktop Claude or Codex adapter is `Remote` (the CLI calls a hosted model; slice 10, later). Every turn carries lane and model used; uar-engineer confirms feasibility (specs 002 and 005 do not name such a field).
Addition from the data input (`design-input-hybrid-skills-data.md` s.2.2, s.3.6, s.4): `Lane` is a closed type (`local` or `remote`) parsed by a function with no default arm that throws on an unknown value; Offline is connectivity, not a lane. Each run stores `lane_requested` and `lane_used` and the chip shows the used lane. A fallback from Local to Remote is allowed only to a lane the user already consented to for that mode (L4); otherwise the turn stops and says why. This narrows spec 005's per-call fallback chains (`docs/005-uar-lite-local-agents.md:72`, `local-onnx → remote-agui`), which as written can send note text off the device silently. A Local run never has a provider id. Embeddings carry their own lane per index, shown separately from the answer lane. Advisory input; the skill that motivates it targets a different app.
Consequence: "Local" is a claim the code can check, not a label the user types. Spec 005 needs a delta (tasks 0.2).
Decider: operator; uar-engineer for the field.

## D12. CSS: shadcn tokens onto Obsidian variables (re-examined)

Conflict: the design binds styling to Obsidian CSS variables through `ipfs-sync-` classes in one `styles.css`, no hex, custom fonts or gradients, the user's accent the only accent (`docs/design/README.md`, `docs/012` decision 2). shadcn components read their own CSS variables (`--primary`, `--background` and so on) and ship a default palette; chat-02 1.4 plans a scoped Tailwind build. `grep -i tailwind docs/design` finds nothing, so the design neither allows nor bans it. The cascade fight with Obsidian's unlayered CSS is untested (chat-01 S3). The prototype `assets/obsidian-shell.css` is not copy-ready (16 hex literals, `--interactive-accent` redefined at line 35 and 76, checked; report D12 lists prototype-only names).

Recommended mapping. shadcn tokens are defined only on the view's root class (`ipfs-sync-root`), never on `:root` and never as a redefinition of an Obsidian variable, and every value is a `var()` of an Obsidian variable:

| shadcn token | Maps to | Note |
|---|---|---|
| `--background` | `var(--background-secondary)` | panel surface (concept section 5) |
| `--card`, `--popover` | `var(--background-primary)` | cards on the panel |
| `--foreground`, `--card-foreground`, `--popover-foreground` | `var(--text-normal)` | |
| `--muted`, `--secondary` | `var(--background-secondary)` | |
| `--muted-foreground` | `var(--text-muted)` | |
| `--accent` | `var(--background-modifier-hover)` | collision: shadcn's "accent" is a hover surface, not the user's accent. Mapping it to `--interactive-accent` would paint every hover in the accent |
| `--accent-foreground` | `var(--text-normal)` | |
| `--primary` | `var(--interactive-accent)` | the one accent: active tab, links, one primary action per surface |
| `--primary-foreground` | `var(--text-on-accent)` | name to verify against Obsidian's variable list |
| `--destructive` | `var(--text-error)` | status colour, semantic only |
| `--border`, `--input` | `var(--background-modifier-border)` | |
| `--ring` | `var(--background-modifier-border-focus)` | |
| radius, font | Obsidian radius and `--font-interface`, `--font-monospace` | names to verify; no font files, no icon font |
| chart, sidebar tokens | not imported | |

Names confirmed in the concept: `--background-secondary`, `--background-primary`, `--background-modifier-hover`, `--background-modifier-border`, `--background-modifier-border-focus`, `--text-accent`, `--text-highlight-bg`, `--font-interface`, `--font-ui-small`, `--font-ui-medium`, `--size-4-*`. Not confirmed anywhere I read: `--text-on-accent`, radius and monospace variable names, success and warning variable names. "Unverified until checked against Obsidian's published list."

Dark mode follows because Obsidian's variables change under `.theme-dark`; no shadcn `.dark` block is imported and `dark:` utilities are avoided (chat-02 1.4 plans a `.theme-dark` variant only if needed).
Contrast: the default light accent with white small text is about 3.6:1 (concept section 5). The default shadcn Button (primary fill, small label) therefore fails on the default light theme. Rule: accent-filled controls are icon buttons or large labels, or use a derived darker fill variable; text buttons use outline or ghost variants. A derived fill via `color-mix` needs `minAppVersion` above 1.12.3 or is avoided (report D12; support unverified).
Gate (slice 01 section 3): a script fails the build on a hex or rgb literal, a gradient, a `font-family` that is not an Obsidian variable, an `@font-face`, a token value that is not a `var()` of an allowed Obsidian variable, a selector outside the root class or prefix, and a redefinition of an Obsidian variable. The spike S3 dump (chat-01) checks computed values on a theme with a non-default accent: the only accent-hued computed colours trace to `--interactive-accent` or `--text-accent`.
Consequence: shadcn components are generated, then restyled by mapping, not by editing each component; any shadcn default that bypasses a token (a literal colour in generated code) fails the gate and is fixed in the generated file, reviewed like our code. If Tailwind output cannot be scoped (S3), the spike's other variants decide (chat-02 1.4).
Decider: operator for `minAppVersion`; uiux-lead through Open Design for the table in the design copy (S8).

## D13. Status bar chip and mobile

## C. Collections and embedding source (slices 03, 04, 05, 09)

Operator input, 2026-10-04: PGlite with vectors, embeddings for user-defined collections. Cited, not re-decided: `docs/006-embedded-stores.md` (user-approved: PGlite for vectors and metadata, pgvector when brute force stops sufficing, SurrealDB WASM for the graph, rebuildable caches keyed by `file_sha256`); `mvp-08-sync-history-store/README.md` (owns the PGlite pin, embeddings not in the snapshot, size budget, phone opt-in, unrun iPhone gate). - **C1 Collection model.** Options: (a) membership as a filter over one shared per-block index, indexing driven by the union of defined collections; (b) a separate embedding store per collection. Recommended: (a). Consequence: storage is the size of the union, once; a document in several collections is embedded once and counts in each; removing a document from one collection does not delete its vectors while another collection (or the union) still includes it; deleting a collection prunes only vectors no remaining collection needs; per-collection cost is computed from membership, not stored. Under (b), a document in k collections costs k times in storage and compute, and phone memory suffers most. The pglite assessment (s.4.2, s.4.1) compares both and recommends (a) with membership materialised at path level, not content-hash level: an edit changes the hash but not membership, so an edited note drops out of results until re-embedded and is queued again (s.4.2). Embeddings keep byte offsets, not chunk text, so no second plaintext copy of every note sits in IndexedDB (s.4.1). Orphan rows pile up with every save, so garbage collection is mandatory (s.4.3 step 6). Its one concession to (b): a per-collection HNSW partial index on desktop only, if measurement ever justifies it (s.4.2, s.2.4). Join latency and planner behaviour are unverified (s.4.1, s.8). Decider: operator, with data-engineer feasibility.
- **C2 Embedding source.** Options: local ONNX or in-WASM model (works offline, compute and memory on the device, unrun iPhone gate) versus the OpenAI-compatible embeddings endpoint of a configured provider (REST only, which is the only mobile option from slice 02). Facts (pglite assessment s.3): the Anthropic-compatible kind cannot serve embeddings (Anthropic offers no embeddings model and points to Voyage AI; the Voyage shape was not read), so only the OpenAI-compatible kind qualifies; a loopback server such as Ollama or LM Studio is an OpenAI-compatible embeddings source that never leaves the device, and under D9 it is `Local`; the local route has packaging problems (`@huggingface/transformers` 4.3.0 depends on native `sharp` and `onnxruntime-node` and on a dev prerelease of `onnxruntime-web`, s.3.1; the int8 MiniLM file is 22.97 MB; first run fetches the model, so "offline" holds only after one online run, s.3.1); PGlite is about 3.4 MB gz wasm plus 1.9 MB gz data (s.0, s.1.1), whose loading inside a single-file plugin bundle is unverified. ## S. Conversation persistence and sync (slice 11)

Operator input, 2026-10-04: "make sure we consider persisting conversations and perhaps syncing those across devices using IPFS." Cited, not re-decided: `chat-00-phase-overview/README.md` decision 3 and `chat-03-chat-shell-and-entities/specs/chat-entities/spec.md` (entity types conversation, message, run, tool call; typed parts; interrupted state; eviction sentinel; vault boundary); D15; D16 (inbox folder, retention); `docs/006-embedded-stores.md` (cache rule, which does not cover conversations because they are authored data, as D15 and pglite assessment s.4.5 say of definitions); `README.md` "conflict policy" and "History growth"; `src/sync/exclusions.ts` (`DEFAULT_EXCLUSIONS`: `.trash/`, `.ipfs-sync/`, `.ipfs-sync-fixture`, `.DS_Store`, `.obsidian/`, `node_modules/`, `.git/`, `.smart-env/`; read 2026-10-04); `mvp-08` (embeddings never ride the snapshot); `mvp-07b-keys-history-guard-release-2/tasks.md` 1.8 (prune bound).

Facts the options turn on (all read in `README.md`, 2026-10-04): the sync is a snapshot with a sequence floor; pull replaces a file this device did not edit, keeps a local edit when only this device changed it, and when both changed the node's version takes the path and local content is kept as `name (ipfs conflict YYYY-MM-DD).ext`; **pull applies no remote deletions** (it leaves remotely deleted files and reports them); every publish that changes something adds one history file of 4 to 14 MB (5,000 to 20,000 files), warning at 1,500, refusal at 1,999; `prune-history` keeps at least the newest 20 and removes only the node's working-tree history files, while earlier published roots stay pinned.

The uncomfortable parts, to be stated in the UI before sync is enabled (S6):
1. IPFS content is immutable. A conversation that was published cannot be erased from older roots or from anyone who pinned them. `prune-history` trims the node's own history files; it does not recall copied blocks.
2. Synced conversations contain note excerpts and model answers. They get the vault's encryption and are readable on every device that holds the vault and its passphrase.
3. A remote provider may have logged what was sent, independent of anything we sync.
4. Chat makes publishes non-empty. The 96-files-a-day arithmetic of the README (15-minute timer, vault changing every tick) times 4 to 14 MB is 384 MB to 1.3 GB of pinned history a day in the worst case (my arithmetic, not a measurement).
5. Remote deletions are not applied on pull, so deleting a conversation on one device does not delete it on another, and a device that still holds the file can republish it.

Options:
- **A. Local-only persistence** as entities in PGlite; sharing only through the existing Save as note. Smallest. No new sync behaviour. Conversations sit in an evictable store (pglite assessment s.1.2) and are authored data, so loss on eviction is real; the eviction sentinel of chat-03 1.2 detects it. No cross-device history.
- **B. Conversations as files in a dedicated vault folder**, one file per conversation, written when a turn completes and debounced, never per token, carried by the existing encrypted sync with no new sync machinery. Evaluation:
  - Format. Markdown with frontmatter is readable and openable but looks like a note: it appears in Obsidian search and graph and to other plugins unless the folder is hidden. JSON or JSONL is not a note and is validated by schema. Recommended format if B is chosen: one JSON document per conversation with `schemaVersion`, because the app, not the user, reads it; Save as note remains the readable path. Open point: `.jsonl` or `.json` visibility in Obsidian's file explorer is unverified.
  - Location and visibility. Options: a normal folder (visible to search, graph, other plugins, and to any "Whole vault" collection) or a dot-folder, which Obsidian generally hides from search and graph (general behaviour, unverified here) yet which still publishes because it is not in `DEFAULT_EXCLUSIONS` (the scanner excludes only by rule: `src/sync/scan.ts` calls the matcher per path). Recommended: dot-folder, and a named exclusion so it is never in an embedding collection, plus never in the vault index, by default. Hidden folders are read and written through the vault adapter, not the note API; slice 11 task 1.1 tests that the sync scans, publishes and pulls it and that Obsidian does not index it.
  - Exclusion from embeddings. Collections (slice 03) must exclude the conversations folder from every union, including "Whole vault", by default; search over conversations is a separate opt-in (S8).
  - Conflict when two devices append to the same conversation. One shared file per conversation produces conflict copies whenever both devices changed it between publishes (README conflict policy) and the node's version wins at the path. Recommended: one file per conversation per originating device (`<conversation-id>` plus a device suffix), written only by that device; the UI merges by conversation id and time. Continuing someone else's conversation on a second device starts a branch with a parent reference, written to the second device's own file. No cross-device append, so no conflict copies by construction. Cost: a continued conversation is several files.
  - History growth. Each changed file makes the next publish non-empty. Recommended: write on turn complete, then coalesce: at most one conversation write batch per publish interval, never inside the last N seconds before a scheduled publish, and a manual "sync conversations now". The 1.8 prune bound is unchanged (floor 20, warning 1,500, refusal 1,999); a vault that already runs near the warning must not enable B without being told (task 2.4 reads the current history count).
  - Deletion. Because pull applies no remote deletions, deleting the file is not a deletion across devices and a stale device can republish it. See S4.
- **C. A separate append-only op-log or CRDT of chat entities** published as its own encrypted IPFS record. Merges without conflict copies, but needs its own sequence floor, fork rules and encryption framing, and the README says true merging arrives with the Phase 2 op-log, which is not built. Larger than the rest of this phase. Defer until a measured need.

- **S1 Persistence and sync option.** Lead's recommendation, under evaluation and not decided: v1 = A; sync = B as an opt-in, off by default, folder excluded from embeddings, write on turn complete; reject C until a measured need. My view after the checks above: agree, with two changes forced by the README facts: B writes one file per conversation per device (S3) and B ships a tombstone rule (S4). Decider: operator, after the D15 ruling.
- **S2 Format and location for B.** Recommended: a JSON document per conversation in a dot-folder, excluded from embeddings, the vault index and every collection by default; the folder name is the owner's. - **S4 Deletion semantics.** Options: delete the file, or write a tombstone (conversation id, deleted time, no content) over it. Recommended: tombstone that replaces the content, kept for a bounded period the operator sets, then removed; the UI says plainly what deletion cannot do (S6 item 1). Data model (entities, per `chat-entities` spec and extended here; owner data-engineer; layering respected: the UI reads stores through hooks, stores call the persistence service, the file writer is a service the store calls):
- `conversation`: id, title, createdAt, updatedAt, mode (Notes or Agent), default collection id, originating device id, parent conversation id and parent message id (for a branch), `deleted` and `deletedAt` (tombstone), `schemaVersion`.
- `message`: id, conversation id, role, ordered typed parts (`text`, `thinking`, `state`, `data`, `confirmation`, `skill-activation`, `memory-recall`, `citation`, `error`, `a2ui-surface`, `unknown`), status, run id, createdAt, lane and model used (D9), provider id (never a key).
- `run`: id, conversation id, status, startedAt, finishedAt, error summary.
- `tool call`: id, message id, run id, name, args text, result text, status. Synced files omit args and results by default.
- Citation parts store references (path, heading, content hash, offsets), not excerpt text, following the pglite assessment's no-chunk-text rule (s.4.1); a stale reference renders as "source changed".
- Never stored: provider keys, secret ids' values, the node token, passphrase material.

Schema and format from the data input (`design-input-hybrid-skills-data.md` s.6; advisory, not committed; the skills it studies are silent on retention, tombstones and erasure, s.6.1):
- Authored tables in a separate additive-only migration, never touched by "Rebuild index": `conversations` (id, mode, title, default scope as collection ids, `profile_version`, origin device, `sync_state` of `local` or `publish-opt-in`, timestamps, `deprecated_at` for soft delete), `runs` (append-only; `lane_requested`, `lane_used`, model id, provider id null iff the lane is local, profile version, scope, `index_model_key`, status, `refusal` of `no-index`, `below-floor` or `out-of-scope`), `messages` (append-only; edit is a new row with `supersedes`; `device_id` and `device_seq`, unique together; typed `parts`), `message_citations` (sentence index, path, `file_sha256`, byte offsets; no text, a changed hash shows "note changed"), `tool_calls` (one row per state transition; `effect_class`, `state` of proposed, approved, denied, running, done, failed, cancelled; `idempotency_id`; redacted args and result). Ids are client UUIDs. No vector column on any of them: embeddings live in their own tables because IdbFs rewrites a table file whole (pglite assessment s.1.2).
- Option B format as the data input proposes it: one append-only JSON Lines file per conversation per device, `Chats/<conversation_id>/<device_id>.jsonl` (a normal folder name is its example; the dot-folder alternative of S2 stays open), each line a self-describing record with `type`, `id`, `ts`, `seq`; readers merge all device files by `(ts, device_id, seq)`; single writer per file, so pull sees no conflict copy; a conversation index is derived into PGlite on read, not synced. That is close to my per-device JSON of S2 and S3; the difference is append-only lines versus a whole document. Whether an appended-to published file re-uploads whole or by segment is unverified (data input s.6.2). S2 stays open between the two.
- Immutability statements required if B or C ships (data input s.6.4): (1) before the first publish of a conversation, a plain statement that publishing is permanent; (2) per-conversation opt-in to sync, default off; (3) Wipe local stores says it does not remove published copies. Evidence: old roots stay pinned and fetchable and the project never unpins (`DESIGN.md:404` as cited there); the vault content key never rotates and a rewrap does not revoke old copies (`DESIGN.md:425-427,457`); the only recovery named is re-encrypting the vault, which is a new vault. Under A none of this applies.
- Mass-removal guard: a bulk "delete all conversations" that removes many published files could trip the guard; thresholds beyond the 49 percent line were not read (data input s.6.2). The bulk delete path tests this.
- `device_id` and `device_seq` exist from the start so B or C can be added without a migration. They publish nothing.

Tie to the PGlite schema (pglite assessment s.4.1, s.1.2): conversations live in the entity store, in their own tables, not in the embeddings, chunks, collections or membership tables. Under `idb://` the whole database is resident memory, so chat tables stay small and separate (own files). Whether chat and sync-history share a database is mvp-08's decision (chat-03 1.2 depends on it). When B is on, the files are the source of truth for synced conversations and the entity store hydrates from them, which makes that store a cache for those conversations and removes the eviction loss; for local-only conversations the store stays authoritative.
