## Goals / Non-Goals

**Goals:**
- One publish code path for CLI and plugin; the plugin adds only a host and a UI.
- A small WebView bundle and bounded memory per file.
- Settings an operator can configure without editing files, with safe validation.
- A reproducible feature operation that never touches the operator's real vault.

**Non-Goals:**
- No pull in the plugin (mvp-05), no encryption (mvp-06), no history store in the plugin (mvp-08 is CLI only).
- No control center (Q7), no agent surfaces, no mobile verification (still unverified, T3).
- No DESIGN.md edit (mvp-10).

## Decisions

1. **Own `rpcCall` (first task).** `src/kubo/rpc-call.ts`: `POST <base>/api/v0/<endpoint>?<args>` via an injectable transport (CLI: `fetch`; plugin: Obsidian `requestUrl`, see the amendment below), auth headers from the existing builder, response mode one of `json`, `ndjson` (last or all lines), `text`, `none`; non-2xx bodies parsed for kubo's `{Message, Code, Type}` and raised as the existing typed errors; 401/403 stay authentication errors. The `KuboClient` interface and every caller stay unchanged; `files/write` (multipart `data`) and gateway reads go through the same transport; the multipart body is built by hand (`src/kubo/multipart.ts`) so both transports send identical bytes. `name/resolve` sends `nocache=true`. Response field names (`Hash`, `Size`, `CumulativeSize`, `Type`, `Entries`, `Keys`, `Path`, `Id`, `AgentVersion`) are read from the library's typings and the existing stub tests, not from memory. Rejected alternative: keep the library and tree-shake; the library's Node-only transitive typings are the reason for the shim, and only about ten calls are used. Size target: probe combined size below 60 KB unminified. If the target is missed, the task reports the measured number rather than relaxing the check silently. The engineer proposes the decision-log entry text; the lead appends it.
> **Amendment 2026-09-30 (transport, from the first real Obsidian run).** The plugin's default transport is `src/plugin/request-url-transport.ts`, an adapter over Obsidian's `requestUrl` with `throw: false`, returning a standard `Response` so 401/403/other statuses map to the same typed errors as with `fetch`. The CLI keeps global `fetch`. `requestUrl` cannot send `FormData`, so `files/write` sends a prebuilt multipart buffer (field `data`, boundary in the Content-Type header) from `src/kubo/multipart.ts` for both transports. Bodies arrive whole, which the engine's bounded transfers (8 MB chunks) already assume. Network errors keep their typed error and now name the transport, with a CORS hint for a browser `Failed to fetch`.

2. **Layout.** `src/plugin/`: `index.ts` (Plugin class, re-exported by `src/main.ts`), `obsidian-host-bridge.ts`, `settings-model.ts`, `settings-migration.ts`, `settings-to-config.ts`, `settings-view-model.ts` (pure, testable), `settings-tab.ts` (Obsidian UI; owned by uiux-lead for layout and copy), `publish-runner.ts` (guard, key flow, events to progress), `adopt-key-dialog.ts`. Layering stays inward: UI -> view model -> runner -> `src/sync` -> `src/kubo`.
3. **Settings model (version 2).** `{version: 2, rpc: {url, port?}, gateway: {url, port?}, publicationKey, mfsRoot, auth: {scheme, ...fields}, userExclusions: string[], ownedKeys: string[], publishIntervalMinutes, kv: {[key]: base64}}`. `settings-to-config.ts` converts it to the raw config layer used by the mvp-01 resolver so the plugin gets the same validation, endpoint composition, JWT warning and node-safety errors as the CLI. The view model maps `ConfigError` codes to inline field errors; an invalid edit is not saved.
4. **Migration.** Pure function of the stored object (see spec). Gateway starts equal to the old RPC URL because the old plugin read through RPC and the shipped defaults use one host for both; the operator can change it. The old default key is deliberately remapped, and migration never touches the network or `ownedKeys`.
5. **Secrets and `data.json`.** Secrets live in plugin data as spec 011 Q4 allows. The gap found here: `.obsidian/plugins/ipfs-sync/data.json` is inside the vault and the mvp-02 default exclusions only list specific `.obsidian/` files, so the token would be published. This change adds `.obsidian/plugins/ipfs-sync/data.json` to the default exclusion list (kept explicit even though the repair of 2026-09-30 added the whole `.obsidian/plugins/` directory: plugin code and data are device-local, and pull refuses such paths). Consequence: `excludesHash` for the default list changes, so the literal-hash test from mvp-02 and any mvp-03 expectations must be updated in the same commit, and devices on different versions will see a divergence warning. Coordinate the edit with whoever owns `src/sync/exclusions.ts` at that moment (mvp-02/03 are being implemented by the same engineer). Alternative considered: keep the hash and filter the file silently; rejected because the hash exists to make divergence loud.
6. **Obsidian HostBridge.** `fs` over `app.vault.adapter` (`list`, `stat`, `readBinary`, `writeBinary`, `mkdir`, `remove`, `exists`), which also reaches hidden folders. `readRange` has no platform primitive: it reads the file with `readBinary` and slices. That is bounded to one file, not one 8 MB range, so a single very large file can still exhaust mobile memory; it is documented in the spec and stays an open risk (T3). `kv` is a `kv` object in plugin data with base64 values, written with `saveData`, merged with settings by read-modify-write so neither clobbers the other. `net` maps to the transport (the plugin passes `requestUrl`). `agent` and `shell` raise not-implemented / denied errors. The bridge rejects absolute paths and `..`. Symlink handling: the Obsidian adapter does not expose lstat, so pull's symlink rule (mvp-03) cannot be met by this bridge; that matters for mvp-05, not here. Recorded now so mvp-05 does not assume it.
7. **Publish runner.** Order: guard (`assertFixtureVault` from marker stat) -> build config from settings -> key classification and creation flow using `ownedKeys` in plugin data -> engine publish with the EventBus -> notice. Progress: a status-bar item and a rolling notice update from `file.changed` events; `publish.complete` produces the summary. One publish at a time (a boolean lock released in `finally`). Auto-publish timer keeps the old setting and calls the same runner in quiet mode; the guard notice appears at most once per session.
8. **Commands.** Publish, Show status. No Pull command until mvp-05 (the old one is deleted with its tar logic; the plugin regresses on pull for one increment and the release notes for v0.2.0 already carry the fixture-only warning). The ribbon icon runs Publish.
9. **Build output.** `esbuild.config.mjs` currently writes the plugin into the operator's real vault. This change makes `pnpm build` write `dist/plugin/main.js` and copy `manifest.json` there, and `pnpm dev` write to the path in `OBSIDIAN_PLUGIN_DIR` when set (the previous behaviour becomes opt-in). Justification: the feature operation installs from `dist/plugin/`, and a production build must not overwrite the plugin that the operator's live Obsidian has loaded. The README dev-loop text needs a follow-up from the documentation-specialist.
10. **Test seam for `obsidian`.** Vitest gets an alias to a small stub module (`Plugin`, `Notice`, `PluginSettingTab`, `Setting`, `Modal`, `TFile`, adapter) under `tests/support/`, so the runner, bridge and tab logic are testable in Node. The stub is test-only and never bundled.
11. **Disjointness from mvp-08 (runs in parallel).** mvp-04 owns `src/plugin/`, `src/kubo/`, `esbuild.config.mjs`, `tests/support/`, `tools/feature-op-mvp-04.mjs`, and the dependency edits this change makes (removing `kubo-rpc-client`; adding nothing). mvp-08 owns `cli/store/` and `src/core/store/` only, plus the `@electric-sql/pglite` dependency line. Shared files: `package.json` and `pnpm-lock.yaml` are single-writer: mvp-04 task 1.1 lands the dependency removal and lockfile first and says so in its task notes; mvp-08 adds its dependency afterwards in a separate commit on top. Neither touches the other's directories; `src/sync/exclusions.ts` (task 2.3) belongs to neither and is edited only by mvp-04 in that one task, with mvp-08 not reading exclusions. If mvp-08 needs a `src/core` change beyond `store/`, it is a separate spec delta.

## Feature Operation

### Constraints
(a) The operator's real vault `/Users/gqadonis/obsidian` is never published or pulled. (b) A cadence checkpoint is one command. (c) No automation route is claimed to work unless observed.

### What was observed on this machine (read-only checks)
- Obsidian is already running with the real vault open (`obsidian.json` lists four vaults; the real one is marked open).
- The app binary at `/Applications/Obsidian.app/Contents/MacOS/Obsidian` acts as the official CLI when given a command: `--help` printed a command list including `command id=<id>`, `commands`, `plugin:enable`, `plugin:reload`, `plugins:restrict on|off`, `reload`, `vaults`, `vault info=name|path`, and a `vault=<name>` option. It also printed "Your Obsidian installer is out of date. Please download the latest installer which includes better CLI support". `vaults verbose` and `vault info=name` succeeded and returned the vault list and the active vault name.
- `obsidian` is not on PATH, so the script must call the app binary by its full path (or a path from an env var).
- Not observed: running `command`, `plugin:enable` or `plugins:restrict` (they mutate app state and were not run), targeting a vault that is not yet registered, and `obsidian://` URI behaviour.
- Danger: without `vault=<name>`, commands target the active vault, which is the operator's real one (`vault info=name` returned `obsidian`).

### Script: `tools/feature-op-mvp-04.mjs` (one process, deterministic parts)
1. Build check: run `pnpm build` and assert `dist/plugin/main.js` and `manifest.json` exist and the bundle contains no Node built-in `require`.
2. Create a throwaway vault in a temp dir named `ipfs-sync-fop04-<random>` and generate the fixture into it with `fixtures/generate-fixture-vault.ts` (marker present, seeded).
3. Install: copy `main.js` and `manifest.json` to `<vault>/.obsidian/plugins/ipfs-sync/`; write `<vault>/.obsidian/community-plugins.json` containing `["ipfs-sync"]`; write `<vault>/.obsidian/plugins/ipfs-sync/data.json` (version 2 settings: endpoints from `IPFS_SYNC_*` env, `publicationKey` `obsidian-vault-sync`, `mfsRoot` `/obsidian-vault-sync/mvp04-demo`, `ownedKeys` read from the stable config `path.join(os.tmpdir(), 'ipfs-sync-feature-ops', 'config.json')` shared with mvp-02/03). If the key exists on the node but is not recorded there, fail with a clear message (`--owned-key` stays the operator escape hatch).
4. Baseline: publish the vault with the built CLI (`--config` at the stable path) so the node holds the first snapshot and the vault holds `.ipfs-sync/state.json`; record the manifest.
5. Edit exactly one fixture note.
6. **Trigger (route-dependent, below):** the plugin's Publish command runs in the throwaway vault.
7. Verify by polling `name/resolve` until the root differs from the baseline (timeout stated in the script), then fetch `<root>/manifest.json` through the gateway and assert: exactly one path has a new sha256, it is the edited note, `rootCID` equals the CID of `<root>/current`, and every other file is unchanged. Run `ipfs-sync status` against the same endpoints and record its output; assert the CID of `<root>/current` equals `manifest.rootCID` in the vault's `.ipfs-sync/state.json` (the plugin's own record).
8. Refusal check (no node request): a second throwaway directory without the marker gets the same install; the trigger runs Publish; assert no new IPNS root and that the vault's `data.json`/state are unchanged. With the manual route this is a second operator step.
9. Confirm afterwards with `files/ls /obsidian-vault-sync` and `key/list` that nothing outside the demo root changed; print every result; exit nonzero on any failed assertion; delete the temp vaults.
10. Evidence the script cannot capture by itself: the Notice text (written and removed counts). The operator or the computer-use step records it (screenshot path noted in the output).

### Trigger route options (what each needs, honestly)
- **A. Official CLI via the app binary.** Needs: the throwaway vault registered with the running app (unverified how to do that without the GUI; `obsidian://open?path=` is one candidate and would add an entry to the operator's `obsidian.json` and open a window), restricted mode off for that vault (`plugins:restrict off`), `plugin:enable id=ipfs-sync`, then `command id=ipfs-sync:publish-vault vault=<throwaway>`. Fully scriptable if it works. Unverified: vault registration, the trust prompt for community plugins, and whether `command` executes with the old installer. Side effects: leaves a vault entry in the operator's Obsidian config; opens a visible window; must always pass `vault=`.
- **B. `obsidian://` URI.** The built-in URI actions I am aware of open or create notes and vaults; running an arbitrary command needs a community plugin, which would be a new dependency in the operator's app. Not recommended. Unverified.
- **C. Computer-use GUI automation.** Needs Accessibility and Screen Recording permission for the driving tool, a visible window, focus stolen from the operator, and fragile coordinates; gives screenshots as evidence. Works with any Obsidian version.
- **D. Operator-assisted.** The script prints exact steps (open the throwaway vault, enable the plugin, run "IPFS Sync: Publish vault"), waits with a timeout for the node to change, and verifies. Always works; a cadence checkpoint blocks on a human.
- **Default (lead decision):** the script does everything except the in-app trigger; the trigger is D or C, recorded as evidence; the script verifies the published result.
- **Recommendation:** implement the trigger behind `--trigger=manual|cli` with `manual` as the default, and add a preflight for `cli` that (1) calls the app binary by full path, (2) confirms `vault=<throwaway> vault info=path` equals the throwaway path before any command, (3) aborts otherwise. Prove route A once during task 7.1 (a supervised run); if it works, the lead may switch the cadence checkpoint to `--trigger=cli`. Until then the checkpoint uses `manual` or the computer-use step.

## Risks / Trade-offs

- [Plugin publish path is first exercised in a real Obsidian only in the feature operation] -> unit tests use an `obsidian` stub; WebView behaviour (memory, `requestUrl` on mobile) is unverified until then, and mobile stays unverified (T3).
- [Large single files on mobile] -> `readRange` loads a whole file (decision 6); fixtures are small; mvp-10 records the outcome for the real vault.
- [The `data.json` exclusion changes `excludesHash`] -> decision 5; any other device on an older build sees a divergence warning by design.
- [Plugin loses pull for one increment] -> accepted; stated in the release notes; mvp-05 follows.
- [Build no longer writes into the live vault] -> dev loop needs `OBSIDIAN_PLUGIN_DIR`; documentation follow-up.
- [Feature operation could touch the real vault by mistake] -> every CLI call carries `vault=<throwaway>` and is preceded by a path check; the script never reads or writes `/Users/gqadonis/obsidian`.
- [Own `rpcCall` regresses a call the library handled] -> the existing client tests are the parity gate; any behaviour the library provided that a test does not cover is listed in the task notes.

## Migration Plan

Users of the previous plugin build: settings migrate on first load (spec). Rollback: `git revert`; the old `src/main.ts` returns with its data format; `data.json` written in version 2 form is not readable by the old build, so users keep a copy of the old file before upgrading (the migration does not delete the source values until saved). Node state: none created except the demo tree and the project key.

## Open Questions

1. **Automation route for the in-app trigger (lead decision needed; recommendation above).** Route A looks viable from the binary's own help text but is unproven for an unregistered throwaway vault and has side effects on the operator's Obsidian config. Recommendation: `--trigger=manual` default, prove route A in a supervised run, then decide whether the cadence checkpoint uses it.
2. **Exclusion change coordination.** Adding `data.json` to the defaults changes `excludesHash` and touches files being edited in mvp-02/03; confirm the order (after mvp-03 merges) or accept a rebase.
3. **Secret storage.** Plugin data is what spec 011 Q4 states; whether a platform secret store is available in the supported Obsidian versions was not checked.
4. **`requestUrl` versus `fetch`**: resolved by the real run (2026-09-30): the node answers `Origin: app://obsidian.md` with 403 and sends no CORS headers on the preflight, so the WebView `fetch` fails with "Failed to fetch". The plugin uses `requestUrl` (amendment below). `requestUrl` on mobile and its `Range` header handling are unverified.
5. **`publishIntervalMinutes`** is kept because it exists today; if the product wants it removed from the first release, say so.
