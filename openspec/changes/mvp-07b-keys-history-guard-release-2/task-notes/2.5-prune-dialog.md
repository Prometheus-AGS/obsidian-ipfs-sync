## Flow
1. The row (hidden until a vault exists) opens the dialog through `keyActions.pruneHistory()`. It needs a local key-slot copy (else the "no vault" notice) and no other operation holding the lock (else "busy").
2. Form: how many history files to keep (a numeric field, no default; the CLI also requires `--keep`) and the current passphrase. The floor 20 comes from the engine's `HISTORY_KEEP_FLOOR`. A count under it is accepted and raised, said in words.
3. Preview (a dry run): `preparePrune` under both locks. One key derivation, every refusal of 1.6, all reads. The dialog shows counts only (removed, kept, total) and the engine's own statements (`pruneStatements`: range of sequences, legacy and duplicate counts, "Checked before this question ... derived from the passphrase you gave", what stays untouched, what can no longer be restored through the current root). No history name or path is copied out of the prepared prune.
4. Review: Cancel first and focused, the question from `prune-history-text.ts`, a remove control that names the count ("Remove 20 history files"). Only an explicit press runs `executePrune`; Cancel, Escape and closing the window never do.
5. Removal: single use; both locks go back whatever the answer.

## Decisions beyond the brief
- **Focus.** The form focuses the count (first required input, as the other key dialogs focus their first field). The review, the only place a destructive control exists, focuses Cancel. A literal "Cancel default focus on the whole dialog" would put a harmless Cancel first on a form that removes nothing; stated here so the reviewer can overrule.
- **Two derivations only if the person adjusts the count.** Changing the count means Cancel and reopen, and the preview derives again. Keeping the vault key in the dialog to re-plan would hold a key longer; not done.
- **Locks held across the preview.** Like Accept: the prepared prune is a view of the node taken under the lock. Publish, pull and the timer show "a key-management action is already in progress" until the dialog closes. A review left open past the lock's 15-minute heartbeat window ends in a refusal at the first write (nothing written); stated limit, same as the mass-removal dialog.
- **A plan that removes nothing holds no lock** and offers only Close.
- **Nothing at the removal step is retryable.** `lock-held` at the token re-check is retryable elsewhere (2.2) but here the review is single use and its lock is gone, so a second press has nothing to act on; the dialog stops with the "may already have changed" text. The text says that this is a possibility, which is conservative when the token check refused before any write.
- **Resume is not in the plugin.** A prune that fails after its journal leaves it for `ipfs-sync prune-history` to finish; the failure text and `MAINTENANCE_WAYS_OUT` say so. `MAINTENANCE_WAYS_OUT` now says the plugin "has no discard action and does not finish an interrupted operation", which is true for rewrap as well (2.2 already had no resume).
- **`PruneHistoryError` added to `SAFE_ERRORS`.** The real-engine test caught it: without this a prune refusal ("the newest history file does not authenticate ...") was shown as the generic line. Its messages are fixed text built from counts and sequences.
- **The unexpected-error line is shared** ("The key action stopped for a reason this plugin does not recognise ... key-slot file ..."). It is accurate but speaks of key slots; a prune-specific line would need the stage (preview wrote nothing, removal may have), so it is left.
- **The one-derivation statement lives in the plugin copy** (`pruneFormStatements`), not in `prune-history-text.ts`: the CLI prints its own derivation line and changing the shared module would touch the CLI tests. The statement the engine already prints after the preview stays in the review.
- **Refusal text can carry up to three escaped node names** (the "manifests/ holds entries that are not history files" refusal, `historyJunk`). That is the engine's existing wording; here it passes `escapeForDisplay` again and is set through `textContent`. The preview itself shows counts only.
- **Cost-confirm seam reused** (2.4): `costConfirmation.policy` is passed as `costPolicy` to `preparePrune`; without the seam the engine refuses a slot above the default cost, as on a command line without a terminal.
