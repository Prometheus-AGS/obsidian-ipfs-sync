# Task 1.8: bound history growth under auto-publish

Role: ipfs-engineer. Date: 2026-10-05. Decision by the lead: do both (a) a minimum interval between auto-publishes and (b) name the supported recovery in the refusal text.

## Decision

(a) Built. `src/plugin/auto-publish-gate.ts` holds `MIN_AUTO_PUBLISH_INTERVAL_MINUTES = 30` and `createAutoPublishTick`. The timer in `src/plugin/index.ts` (`rearmAutoPublish`) still fires at the user's interval; its callback is the gate. A tick sooner than 30 minutes after the previous completed automatic run, or while a run is going, is skipped, not queued. The wait starts when a run ends, also when it failed. The gate lives for the plugin load, so re-arming after a settings change does not reset it. The Publish command and the ribbon icon call `publishVault()` directly and are not gated. The interval setting description (`settings-tab-copy.ts`) states the minimum, that the Publish command is not limited, and that each publish that changes the vault adds one history file.

(b) Already in the tree before this task: `historyFull` (`src/sync/publish-refusals.ts`) and the 1,500 warning (`assessHistoryCount`, `src/sync/history-check.ts`) name `ipfs-sync prune-history <vault> --keep <n>` and "Prune history in the Encryption section of the plugin settings". `src/sync/history-check.ts` was not changed. New tests pin the text.

## Why 30 and not 5

The lead's example was 5 minutes. The acceptance asks that 30 days with a vault that changes on every tick stays under 1,500. Observed (simulated clock, awaited ticks, vault changed on every tick, 43,200 minutes):

| timer interval | minimum | manifests in 30 days |
| --- | --- | --- |
| 1 min | none | 43,200 |
| 1 min | 5 min | 8,640 |
| 1 min | 29 min | 1,490 |
| 1 min | 30 min | 1,440 |
| 5 min | 30 min | 1,440 |
| 15 min | 30 min | 1,440 |
| 30 min | 30 min | 1,440 |
| 60 min | 30 min | 720 |

Five minutes cannot meet the acceptance; the least value that does is 29 (1,490), 30 is the round value with margin (1,440, 60 under the warning). 30 days of continuous change is the worst case; at 1,440 the folder reaches the warning in about 31 days, which is where `prune-history` (1.6, plugin action 2.5) takes over. A one-line change of the constant moves the numbers; the test derives its floor from `HISTORY_WARN_AT`.

The shipped default is `publishIntervalMinutes: 0` (timer off), so the default adds no manifests. The "shipped default timer" in the task text has no cadence of its own; the simulation uses the shortest setting the field accepts (1 minute) as the worst case.
