# 7.5 Stricter not-found handling at the start of a non-first publish

Result (2026-10-05, lead): the shared node does not distinguish not-found from timeout. Not distinguishable, so no stricter rule was added.

Observation. `POST /api/v0/name/resolve?arg=/ipns/<id>&nocache=true&dht-timeout=5s` on https://ipfs.prometheusags.ai:
- a key the node holds (`k51qzi5uqu5dicwvxyvqgk8iwhp7f4r30i7mj54qz3100sln5czk5xcp48jgqq`): HTTP 200 in 0.27 s, `{"Path":"/ipfs/…"}`.
- a well-formed key ID that nobody published (`k51qzi5uqu5dgg6a3sgmw7ju8xr3d2jf4kknt3tdaj1ui4k0ynlwqf0n4cqa7c`): HTTP 500 after 5.2 s, `{"Message":"could not resolve name","Code":0,"Type":"error"}`.

The 5.2 s is the dht-timeout. The same message and status would follow a name that exists but whose record the DHT did not return in time. Nothing in the reply separates "never published" from "not found yet".

Consequence. Per the task text, the refusal rule (refuse when local state has a non-null `rootCid` and the key was not created in this run) is only opened if the node distinguishes the two. It does not, so the 07a baseline stands: a not-found at the start of a publish is accepted. A hostile or flaky node can still make a non-first publish look first. The publish still checks the sequence floor and the previous manifest identity, which is the control that applies. Revisit if kubo starts returning distinct errors.
