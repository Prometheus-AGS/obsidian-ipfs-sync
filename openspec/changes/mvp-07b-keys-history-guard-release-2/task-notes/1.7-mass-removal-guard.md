# Task 1.7: mass-removal guard in the engine

Status: engine and CLI done; the plugin dialog on a manual publish is not part of this task's file list and is open (see below).

## What it does

`guardMassRemoval` (src/sync/publish.ts) runs after the plan and the idle check and before `guardReupload`, the writer-cap check, the name start and the transfer. The arithmetic is `assessRemovals` in src/sync/removal-guard.ts (pure, no host imports).

- Entries before the publish = the baseline manifest's paths (carried entries included, so a carried `CON.md` counts as kept).
- Exclusion-driven group = removed paths and dropped carried paths that the effective exclusion matcher matches. Listed in the result (`exclusionRemoved`) and the CLI note, counted in neither numerator nor denominator.
- Dropped carried entries that the matcher does not match left for an unsafe path shape: outside the count entirely (no honest publisher wrote them).
- Stop when the other removals equal every remaining entry, or, with at least two remaining, exceed half (`others * 2 > remaining`). Exactly half proceeds.
- No baseline (first publish): no check.
- Confirmed by `allowMassRemoval: true` or `confirmMassRemoval(counts)` returning true. With neither the engine throws `PublishRefusedError` code `mass-removal`. The plugin timer passes neither, so it refuses without a dialog.

## Stated limits for task 5.1 (README, DESIGN section 8, release notes)

The checker holds the exact sentences; these are the facts they must carry.

1. Removal of 49 percent of the entries is silent. The guard stops "every entry" and "more than half"; half and below proceed unasked.
2. The publisher does not detect silent per-file corruption of unchanged files by someone with write access to the node (W-14).
3. An unmounted or emptied vault directory shows as all files missing and is caught; the refusal says the two look the same.

## Observed behaviours worth knowing

- `assertHistoryReady` runs during node assessment, before the plan, and may remove junk in `manifests/` (existing behaviour). "Stops before any node write" holds for the transfer, blob removals, manifest, name publish and local state; a node with junk in `manifests/` is cleaned first. The tests use a clean node.
- A vault emptied by `ipfs-sync` on a device with a state file reaches the guard (not `EmptyVaultError`, which is first-publish and repair only).
- Existing test `encrypted-publish.test.ts` "publishes the vault when every file was deleted" now passes `allowMassRemoval: true`.
