## Goals / Non-Goals

**Goals**
- A passphrase can be changed and the cost raised without re-encrypting, with honest statements about what is not revoked.
- The history folder can be pruned without harming old roots.
- The fixture policy lives in two modules, the post-removal tree exists and is reviewed before anything ships, and the release is refused unless evidence binds the shipped bytes to the reviewed tree and to an in-Obsidian run.
- The evidence says what it is: attestations, not proofs.

**Non-Goals:** revocation or VCK rotation, multi-writer merge, user-chosen passphrases (deferred in mvp-06), device pairing, padding, mobile verification beyond a timing measurement, the history store (mvp-08), the real-vault run (mvp-10), a fixture-only fallback release (open question 3).

### 2. Rewrap (`keys change-passphrase`, `keys increase-cost`)
Requires: the device is up to date with the node (07a rule: node sequence and identity equal the record; `complete` is not required because a rewrap reads no local vault file), holds the vault unlocked or the passphrase, holds `publish.lock` for the whole operation (Q-23), and no maintenance or publish journal is pending. Steps: derive from the current passphrase a second time to obtain the raw vault key bytes inside `rewrapKeySlots` (never outside `key-slots.ts`); obtain the new passphrase (generated only; the same passphrase is allowed for `increase-cost`); choose the cost; derive the KEK with a fresh 16-byte salt; build a new slot with a fresh slot identifier, wrap nonce and commitment; overwrite the raw key bytes.
- **The new file contains only the new slot.** The old passphrase therefore fails against the node's current `keyslots.json` and succeeds only against copies in earlier pinned roots. If the current file contains any slot of a type this version does not understand, rewrap refuses ("cannot rewrap a file with slot types this version does not know"). Up to two passphrase slots are tried at unlock (`KEY_SLOTS_MAX_TRIED`); appending would have left the old passphrase valid and cost two derivations.
- **Cost is never silently lowered.** New memory and iterations must each be at least the current slot's; a lower choice needs an explicit downgrade confirmation that shows both. Presets stay within the mvp-06 ceilings (131,072 KiB, 4 iterations).
- **Same-passphrase cost increase** is allowed and the command and dialog state that it does not protect against an attacker holding the old pinned slot at the old cost. Re-read 2026-10-03: `createKeySlotsInternal` requires a `GeneratedPassphrase` (`assertGenerated`, `key-slots.ts:169`), so `rewrapKeySlots` has two input modes: a generated new passphrase (change-passphrase) and "reuse the unlocking canonical passphrase" (increase-cost). A cost above the default (`DEFAULT_KDF_PARAMS`) makes `enforceCostPolicy` refuse on every device that cannot answer a cost question; the plugin has no cost dialog (task 2.4), and unlocking the current slot above default needs `costPolicy` as well.
- **Post-publish test unlock.** After `name/publish`, the command fetches `keyslots.json` from the new immutable root, unlocks it with the new passphrase (one more derivation) and compares the result; on failure it reports loudly that another device's rewrap may have won and the new passphrase may not open the vault, and does not update the local copy.
- Order of effects, each recorded as a phase in the maintenance journal (decision 4): `journaled` (type `rewrap`, pending bytes) -> `file-written` (`keyslots.json` in the MFS root) -> `snapshotted` -> `published` (`republish-root`: snapshot, read-back through the immutable path, pin, name re-resolve check, `name/publish`) -> `local-updated` (local copy and `keyslotsSha256` in state) -> journal deleted. `manifest.enc` and the sequence are untouched.
- Old slot copies and old passphrases remain valid in every earlier pinned root. The command prints this before the confirmation works; the dialog gates its confirm on an acknowledgement.

### 3. Accept changed slots (`keys accept-slots`)
After another device's rewrap, this device's copy differs from the node's file and automatic operations refuse (07a). The action takes `publish.lock` (it writes the local copy and the state hash). It resolves the name once (`nocache`) to one immutable root CID R, fetches `keyslots.json` and `manifest.enc` of R only from R; unlocks the fetched slot with the entered passphrase; authenticates R's `manifest.enc` under the resulting key; requires equal `vaultId`; applies the 07a sequence verdict to R's manifest (a lower sequence needs the explicit-target rollback flag, exactly as a pull); writes the exact bytes that unlocked as the new local copy; updates `keyslotsSha256` in the state and in a pending publish journal if one exists; clears a stale maintenance journal (decision 4); reports. If the new slot's cost is lower than the current copy's in memory or iterations, it shows both costs and requires confirmation (the downgrade warning).
**Restore across a rewrap (C-08).** The 3-step flow applies only to `pull --root-cid <old root>`: that target reads the old root's `keyslots.json`, which differs from the local copy, so the pull refuses and names `keys accept-slots --root-cid <old> --allow-rollback`; after accepting, the copy is the older slot (older passphrase, possibly lower cost), the pull runs, and a further accept of the current root returns the copy to the current slot. `pull --manifest <cid>` and the plugin's Restore action read the history entry under the current root (which holds the current slot) and fetch blobs that are encrypted under the vault key, not under a slot; they need no accept. Stated as the defined, awkward flow for `--root-cid` only.
A slot file that unlocks but whose manifest does not authenticate is never accepted: the manifest proves the vault key, not the slot's freshness, so any genuine slot of the same vault passes; the sequence rule and the downgrade confirmation are the freshness defences.

### 4. Maintenance journal and the republish primitive
`rewrap` and `prune` use `maintenance.<h>.json`, a separate file with `MAINTENANCE_JOURNAL_VERSION = 1`, a `type` field and a `phase` field (`journaled`, `file-written`, `snapshotted`, `published`, `local-updated` for rewrap; `journaled`, `removing`, `snapshotted`, `published` for prune), never `journal.<h>.json`. `republish-root.ts` is the one implementation of: snapshot the MFS root, read it back through the immutable path and check the listed names and bytes that the operation changed, pin, re-resolve the name and compare with the start (07a rule), `name/publish`. Publish and pull refuse with a typed error naming the pending maintenance operation when the maintenance journal exists; rewrap and prune refuse when a publish journal exists. A cross-test runs every combination: publish journal present x rewrap, rewrap journal present x publish, prune journal present x pull, a damaged file of either kind.
**Resume and the dead ends (Q-19).** Resume reads the phase. At `published` or later, the remaining steps only update the local copy and delete the journal. A resume whose name re-check finds the name equal to the journal's recorded snapshot root treats `republish` as done (it does not refuse on its own publication). A lost rewrap race (the node file matches neither the journal's bytes nor the old bytes) is refused with a message that names `keys discard`. `keys discard` removes the maintenance journal after a confirmation and touches nothing on the node; `keys accept-slots` clears a maintenance journal whose pending bytes are no longer on the node. Every refusal from publish, pull, rewrap and prune that is caused by a maintenance journal names `keys discard` and `keys accept-slots`. Rewrap, accept and prune take `publish.lock` (Q-23), because rewrap and prune snapshot the shared MFS tree.
**Re-read 2026-10-03 (corrections to the paragraph above; tasks 1.3, 1.4, 1.6).** (1) "`keys discard` touches nothing on the node" is true only if the primitive withdrew its write: a lost rewrap or prune race has already put the loser's `keyslots.json` (or removed history files) into the shared MFS tree, as 07a's D-1 did for `manifest.enc` (`publish-commit.ts:182-212`). `republish-root` therefore withdraws on `NameMovedError` (rewrap restores the old `keyslots.json` bytes only when the file still holds the journal's bytes and the old bytes equal the file inside the moved root; prune re-adds nothing, the removed files are in the old pinned root). (2) The primitive carries 07a's A-01 guards (read `manifest.enc`, read the name start, re-read `manifest.enc`, compare) and reuses `assertNameUnmoved`, `assertNameStillAt`, `createCommitNode.publishRoot` and `createSnapshotVerifier`. (3) Rewrap and prune change the root CID, so the final step writes `rootCid` and `keyslotsSha256` into the state; otherwise the next publish, on every device, writes a no-change manifest and a history file. (4) The up-to-date check includes the sequence floor (`classifySequence` `in-sync` plus `assertNotBelowFloor`), one shared helper for rewrap and prune. (5) `abandonVault` moves the maintenance journal too.

### 5. `prune-history`
`ipfs-sync prune-history --keep N` removes the oldest `manifests/*.enc` entries from the working MFS tree so that N remain (at least 20 regardless of N; N counts files). Ordering comes from 07a's names: prefixed entries by sequence, legacy entries before all of them with no order among themselves; if N is less than the prefixed count, legacy entries are removed first; if the prefixed count is less than N, the legacy ones fill the keep set in name order (arbitrary, stated in the confirmation: no released build wrote legacy names). Refuses unless, all of which are checked before anything is removed (Q-20): the newest prefixed entry decrypts with the vault key, belongs to the vault, has an inner sequence equal to its prefix, **and that sequence equals the node manifest's sequence** (a node that withholds the newest history files fails this); each of the newest 20 prefixed entries decrypts and has an inner sequence equal to its prefix (one rule, used in the spec, the tasks and here); the device is up to date (`complete` is not required); the command holds `publish.lock`; no publish or maintenance journal is pending. Duplicate prefixes (two files with one sequence, which a fork produces) are counted and shown in the confirmation; they are not a refusal. Shows the counts (removed, kept, legacy, duplicates) and asks for confirmation; removes one path segment under `<mfsRoot>/manifests/` at a time, non-recursively (`assertMfsMutationPath`); then `republish-root`. It never touches `current/`, `manifest.enc` or `keyslots.json`; old roots stay pinned and their history files stay as they were in those roots. The publisher's 1,500/1,999 messages (`history-check.ts`) lose the parenthesis "(not available in this build)".

### 6. Mass-removal guard
In the publish engine, after the diff and before any write, the planned removals are split into two groups: removals caused by the exclusion list (paths that are in the baseline and match the effective exclusion list, for example `.obsidian/*` entries of an older build on upgrade day) and all others (Q-10). The exclusion-driven group is listed and counted in the message but counts in neither the numerator nor the denominator; carried entries (07a) count as kept entries. If the other removals equal every remaining entry, or exceed half of them (entries before the publish, excluding the exclusion-driven group, >= 2), the publish refuses with a typed error unless the caller confirmed: CLI `--allow-mass-removal` or an interactive yes; plugin: a dialog on a manual publish; the timer never opens a dialog and refuses. Limits (W-15): removing 49 percent is silent; a vault directory that is merely unmounted shows as all files missing and is caught; silent per-file corruption of unchanged files by a node writer (W-14) is not detected by the publisher and is stated in the docs and the release notes. The message blames an unmounted or emptied vault only when the exclusion-driven group is not the cause of the count.

## Risks / Trade-offs

- [The branch build can publish real notes] -> never installed on a real vault by any task; `main` keeps the guard; docs warn; the operator run uses throwaway vaults with the real vault path refused by the script.
- [Checker items can be forged by repository writers] -> stated; git-history binding or a signature against a trust anchor that lives outside the repository and is enrolled on a terminal; the hash covers everything that ships; the required lists live in the checker, not in the records.
