## New findings
- **C5-01 LOW — `abandoned-*` latch evidence is inert in the plugin.** `obsidian-kv.ts:63` (`createFolderKv.list`) keeps only `entry.kind === "file"` and `abandoned-<h>-<ms>` is a directory; the CLI Node kv uses `readdir` names (`cli/node-host-bridge.ts:167-170`) which include directories. In the plugin the latch rests only on `encrypted-seen.json`; if that file is deleted while the backup folder stays, pull is unlatched, contrary to DESIGN 8.5 and the runbook. The test at `tests/unit/pull-encrypted-root.test.ts:183-189` creates the name as a file with `kv.set`, hiding this. Fix: let the plugin `list` return folders matching `ABANDONED_BACKUP`, or check for them directly in `isLatched`; test on the folder kv; or drop the claim from the docs.
- **C5-02 LOW/MEDIUM — token check at acquire, not at the first write.** `publish-runner.ts:241`; `assertHeld` is synchronous and consults only the last heartbeat result. A CLI linking `publish.lock` after the plugin's `exists` check and before its rename is overwritten on platforms where rename replaces; the read-back passes; both can write for up to ~60 s. Fix: an async `verifyHeld` from a pre-first-write hook in the engine, or state in the docs that the overlap is bounded by one heartbeat interval.
- **C5-03 LOW — clear-stale-lock does not hold the sync lock while it works.** `stale-lock.ts:61` checks `holder()` once then awaits; a timer publish starting in between makes the clearer's `moveAside` move the publisher's new lock; the publisher's read-back throws `lock-held`; the clearer puts the publisher's lock back, leaving a fresh lock with no holder that blocks the vault for 15 minutes (host name is this session's, never recognised dead). Fix: take the sync lock for the whole `clear()` (new operation kind) and re-check `holder()` immediately before `moveAside`.
- **C5-04 LOW — a lock can be left dangling by the read-back.** `adapter-lock-file.ts:113`: if `readLock` throws after our rename succeeded, `createExclusive` rejects with our lock file on disk, no heartbeat, no holder; blocks 15 minutes. New with R5-01. Fix: wrap the read-back in try/catch and remove the file if it holds our bytes.
- **C5-05 LOW — two independent lock-file instances.** `index.ts:87` builds one `createAdapterLockFile` for the stale-lock control, `publish-runner.ts:165` another; their `holding` sets are separate. A moved-aside `.taken` file keeps the old heartbeat mtime, so the other instance's sweep can delete it; after a plugin reload `holding` is empty and the sweep removes it; "kept under a temporary name" (`stale-lock.ts:77`) is unreliable (the clearer's put-back bytes are in memory). Fix: share one instance, or never sweep `.taken` files.
- **Cosmetic, R5-04 side effect:** `lock()` sets `inFlight = undefined`, so after an abandon a second Publish can open a second unlock dialog over the first (the old dialog is cancelled by the generation check); `settling` deduplication not verified.
- **Cosmetic:** `FIXTURE_ONLY_PULL_NOTICE` (`pull-notices.ts:14`) says "no files outside .obsidian/" but the guard also ignores `.ipfs-sync/`. The stale "encryption is not available yet" text in `pull-guard.ts` is gone.
