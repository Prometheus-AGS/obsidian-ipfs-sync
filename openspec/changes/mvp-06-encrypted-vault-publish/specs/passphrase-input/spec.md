## Purpose

Defines how the passphrase enters the CLI and the plugin, how it is generated, kept and dropped, and what the user is told at setup, so the secret is never logged, stored or passed where it can leak. Passphrases are generated by the product; choosing one's own is a deferred feature.

## ADDED Requirements

### Requirement: CLI passphrase sources
To unlock an existing vault (publish now, pull later), the CLI SHALL read the passphrase from exactly one of: the environment variable `IPFS_SYNC_PASSPHRASE`; a file named by `IPFS_SYNC_PASSPHRASE_FILE`; or, when standard input is an interactive terminal and neither is set, a prompt that does not echo. It SHALL refuse to run when both variables are set. On POSIX systems it SHALL refuse a file whose permissions allow group or other access (it must be 0600 or stricter), a file that is a symbolic link, and a file owned by another user; on systems without POSIX modes it SHALL refuse a symbolic link and a foreign-owned file where ownership can be determined, and SHALL warn that permissions cannot be verified. Only a terminating line feed or carriage-return-line-feed SHALL be removed from file or prompt input. The CLI SHALL NOT accept the passphrase as a command-line flag, from a configuration file, or from a project file. The input SHALL then pass the canonical-passphrase function of the key-slots specification. If no source is available the command SHALL fail with the passphrase-required error before any request.

#### Scenario: Flag rejected
- **WHEN** a `--passphrase` flag is given
- **THEN** the CLI rejects it as an unknown option and states that the passphrase comes from the environment, a file or a prompt

#### Scenario: Non-interactive without a source
- **WHEN** standard input is not a terminal and neither variable is set
- **THEN** the command fails with the passphrase-required error

#### Scenario: Both variables
- **WHEN** both `IPFS_SYNC_PASSPHRASE` and `IPFS_SYNC_PASSPHRASE_FILE` are set
- **THEN** the command fails and asks for exactly one

#### Scenario: Permissive or foreign file
- **WHEN** the passphrase file is readable by other users, is a symbolic link, or is owned by another user
- **THEN** the CLI refuses it and names the problem

#### Scenario: Not a generated passphrase
- **WHEN** the supplied text is not a valid generated passphrase (wrong length, wrong alphabet, or a failed check)
- **THEN** the CLI rejects it with the `passphrase-format` error before any request

#### Scenario: Not in output
- **WHEN** a publish runs with `--show-request` and a passphrase source set
- **THEN** neither the trace nor any other output contains the passphrase

### Requirement: Interactive prompt behaviour
The interactive prompt SHALL read raw bytes without echo, SHALL handle Ctrl-C and Ctrl-D by aborting without leaving the terminal in raw mode, SHALL restore the terminal mode on every exit path, SHALL make backspace delete one character, and SHALL accept pasted input. It SHALL enforce an upper limit of 256 bytes on the input.

#### Scenario: Interrupt
- **WHEN** the user presses Ctrl-C at the prompt
- **THEN** the command aborts and the terminal is back in its normal mode

#### Scenario: Paste
- **WHEN** a generated passphrase with separators is pasted
- **THEN** it is accepted and canonicalised

### Requirement: Vault creation happens only in `ipfs-sync init`
The CLI SHALL create a vault only through the command `ipfs-sync init`, which generates the passphrase itself; `publish` SHALL never create a vault. On an interactive terminal, `init` SHALL generate the passphrase, show it once in a monospace font in 5 groups of 5, show the instruction to save it in a password manager together with the no-recovery consequence text, and require the user to enter it again (the check symbols make typos detectable) before the vault is created. Non-interactively, `ipfs-sync init --passphrase-file <path>` SHALL generate the passphrase and write it to `<path>` with mode 0600 by exclusive creation, SHALL refuse to overwrite an existing file, SHALL refuse a symbolic link at the path and a directory that is a symbolic link or owned by another user, SHALL print only the path and never the passphrase, and SHALL then create the vault; on systems without POSIX modes it SHALL state plainly that no mode check exists. An externally supplied passphrase SHALL NOT be accepted at creation. Choosing one's own passphrase is not supported.

#### Scenario: Mismatch
- **WHEN** the re-entered passphrase differs
- **THEN** no vault is created and nothing is sent to the node

#### Scenario: Automated setup
- **WHEN** `ipfs-sync init --passphrase-file <path>` runs and the path does not exist
- **THEN** the file is created with mode 0600, only the path is printed, the consequence text goes to standard error, and the vault is created

#### Scenario: Existing file
- **WHEN** the path already exists, or is a symbolic link
- **THEN** the command refuses before any request and writes nothing

#### Scenario: Passphrase never printed
- **WHEN** `init` runs non-interactively
- **THEN** neither standard output nor standard error contains the passphrase

#### Scenario: External passphrase
- **WHEN** `init` is run with `IPFS_SYNC_PASSPHRASE` or `IPFS_SYNC_PASSPHRASE_FILE` set to any value, including a valid-looking generated one
- **THEN** the value is ignored for creation, because the passphrase is generated by the command

#### Scenario: Publish never creates
- **WHEN** `publish` runs against a root with no vault
- **THEN** it refuses with a message pointing to `ipfs-sync init` and sends no write

### Requirement: Handling in memory
The CLI SHALL hold the passphrase as bytes, SHALL overwrite the bytes and every intermediate after key derivation, and SHALL NOT log, trace or persist them. The documentation SHALL state what cannot be guaranteed: the environment variable remains readable by the same user's processes and can land in shell history or CI logs, the runtime may keep copies of strings, and the file source is preferred over the variable for automation.

#### Scenario: Documentation
- **WHEN** the CLI help and README are read
- **THEN** they state the environment-variable exposure and recommend the prompt for interactive use and the file for automation

### Requirement: Plugin session key
The plugin SHALL prompt for the passphrase at most once per session, keep the unlocked key in memory only, never write the passphrase or any key to `data.json`, the local state or any log, and discard the key when the plugin unloads or the user chooses to lock. The unlocked key SHALL be held as a non-extractable key object. The specification SHALL state that other code in the same context could use that key object, and that the dialog holds the passphrase in an interface string that cannot be zeroed.

#### Scenario: One prompt per session
- **WHEN** the user publishes twice in a session
- **THEN** the passphrase dialog appears once

#### Scenario: Nothing persisted
- **WHEN** the plugin's stored data is searched after an unlocked session
- **THEN** it contains no passphrase, key or key-derived value

#### Scenario: Lock
- **WHEN** the user locks the vault
- **THEN** the next publish asks for the passphrase again

### Requirement: Plugin first-time setup
The plugin's Publish command, when no vault exists, SHALL open the setup dialog instead of creating anything; only the dialog's Create action creates the vault. The setup dialog SHALL generate a passphrase (23 random symbols plus 2 check symbols, shown in 5 groups of 5 separated by hyphens, in a monospace font, with the note that letters are case-insensitive), tells the user to save it in a password manager, and requires re-entry. It SHALL offer no field for choosing one's own passphrase. The dialog SHALL state that a lost passphrase means permanently lost data with no recovery and SHALL require an explicit acknowledgement (a checkbox) before the vault is created. It SHALL refuse a mismatched re-entry with a text error.

#### Scenario: Acknowledgement required
- **WHEN** the passphrases match but the no-recovery acknowledgement is unchecked
- **THEN** the create button is disabled

#### Scenario: Consequence text
- **WHEN** the dialog is displayed
- **THEN** it states that there is no recovery and that data is lost if the passphrase is lost

#### Scenario: Typo reported locally
- **WHEN** the unlock dialog receives a passphrase whose check fails
- **THEN** it reports a probable typo without contacting the node

#### Scenario: No own passphrase
- **WHEN** the dialog is inspected
- **THEN** it contains no control for entering a passphrase of the user's choosing

### Requirement: Unattended triggers never prompt
Automatic publishing (the timer) SHALL NOT open a passphrase dialog. When the vault is locked it SHALL skip the publish and show at most one notice per session explaining that the vault is locked.

#### Scenario: Timer while locked
- **WHEN** the timer fires and the vault is locked
- **THEN** no dialog opens and no request is sent

### Requirement: Responsive key derivation
Argon2id SHALL run in a form that yields to the host's event loop at intervals of at most 10 milliseconds of computation, so the Obsidian interface stays responsive; while it runs, the interface SHALL show that the vault is being unlocked and SHALL tell the user to keep the application in the foreground (a backgrounded web view may throttle the work). One derivation with the default parameters SHALL be measured in the foreground on the development machine and recorded, against the targets of at most 3 seconds and no event-loop gap above 100 milliseconds. If a target is not met, the report SHALL say so and the lead decides; the target SHALL NOT be weakened silently. A measurement on a phone is not part of this change and is a precondition for lifting the marker guard.

#### Scenario: Event loop gaps
- **WHEN** a default-parameter derivation runs while an event loop delay monitor samples
- **THEN** the largest observed gap is below 100 milliseconds on the development machine, or the report states the measured value and that the target was missed

#### Scenario: Timing recorded
- **WHEN** the feature operation runs
- **THEN** the derivation time with default parameters is printed and recorded

#### Scenario: Foreground text
- **WHEN** the unlock indicator is shown
- **THEN** it tells the user to keep the app in the foreground

### Requirement: Dialog accessibility
The setup and unlock dialogs SHALL have visible labels, text errors associated with their fields, masked input with a control to reveal it, keyboard operation and no reliance on colour alone.

#### Scenario: Keyboard
- **WHEN** the user tabs through the setup dialog
- **THEN** every control receives focus in reading order and Enter submits only when the form is valid
