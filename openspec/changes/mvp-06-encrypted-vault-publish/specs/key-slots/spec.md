## Purpose

Defines the vault content key, the passphrase key slot that protects it, the public `keyslots.json` that stores the slot, and the rules that decide whether a passphrase and a slot are acceptable, so that unlock and first-time setup fail closed and a hostile slot file cannot weaken the derivation or exhaust the device.

## ADDED Requirements

### Requirement: Vault content key and vault identifier
When a vault is first published, the device SHALL generate a random 256-bit vault content key (VCK) and a random 128-bit `vaultId`. The VCK SHALL never be stored or transmitted in plaintext. The `vaultId` is public, SHALL be recorded in `keyslots.json` and in the local state, and SHALL be bound into the associated data of every wrap, blob and manifest encryption.

#### Scenario: Fresh vault
- **WHEN** a vault is set up
- **THEN** the VCK and `vaultId` are new random values and no earlier vault shares either

#### Scenario: No plaintext VCK
- **WHEN** every byte written to the node and to the local `.ipfs-sync/` folder is searched for the VCK (raw, hex and base64 forms)
- **THEN** none is found

### Requirement: Passphrase slot with key commitment
The VCK SHALL be protected by a passphrase slot. A key-encryption key (KEK, 32 bytes) SHALL be derived from the canonical passphrase with Argon2id (version 0x13, random 16-byte salt). Two independent 32-byte values SHALL be derived from the KEK with HKDF-SHA256 using the `vaultId` as salt: a wrap key with info `ipfs-sync/slot/wrap/v1`, and a commitment with info equal to the bytes `ipfs-sync/slot/commit/v1` followed by the slot identifier (16 bytes), the KDF version (unsigned 32-bit, 19), memory in KiB, iterations, parallelism, output length (32), each as unsigned 32-bit big-endian integers, and the salt (16 bytes). The commitment SHALL be stored in the slot. Unlock SHALL proceed in this order and stop at the first failure: validate the fixed fields and parameter bounds; run Argon2id; derive the commitment; compare it with the stored one in constant time; derive the wrap key; decrypt with AES-256-GCM. Every HKDF output in this change (wrap key, commitment, name key, manifest key, file key) SHALL be 32 bytes. The identifiers `vaultId`, slot identifier and file identifier are 16 random bytes; wherever one appears in associated data or as an HKDF salt, its raw 16 bytes (the hex text decoded) SHALL be used, not the hex text. The VCK SHALL be encrypted under the wrap key with a random 96-bit nonce, and the associated data SHALL be the concatenation of the label `ipfs-sync/slot/v1`, the raw `vaultId`, the raw slot identifier, the KDF version (19), memory, iterations, parallelism and output length (32) as unsigned 32-bit big-endian integers, the 16-byte salt, the bytes of `argon2id`, a single 0x00 byte, and the bytes of `aes-256-gcm`. The default parameters SHALL be memory 65,536 KiB (64 MiB), 3 iterations, parallelism 1.

#### Scenario: Unlock with the right passphrase
- **WHEN** the slot is opened with the passphrase used at setup
- **THEN** the original VCK is recovered

#### Scenario: Commitment checked first
- **WHEN** the stored commitment is altered and the right passphrase is used
- **THEN** unlock fails with the wrong-passphrase-or-damaged-slot error before any decryption, including through the test-only key hook

#### Scenario: Parameters bound
- **WHEN** the stored memory parameter is changed by one and the slot is opened with the right passphrase
- **THEN** unlock fails with the wrong-passphrase-or-damaged-slot error

#### Scenario: Fixed fields exact
- **WHEN** a passphrase slot declares a KDF version other than 19, an output length other than 32, or an algorithm string other than the expected ones
- **THEN** the whole unlock is refused with the unsupported-format error before any derivation

#### Scenario: Commitment vector
- **WHEN** the commitment is derived from fixed inputs
- **THEN** it equals the recorded fixed-output vector

### Requirement: Generated passphrases only, with a check
Passphrases in this change SHALL be generated by the product; user-chosen passphrases are not offered. A generated passphrase SHALL have 25 symbols from the uppercase RFC 4648 base32 alphabet (letters A to Z and digits 2 to 7): 23 random symbols (115 bits) followed by 2 check symbols. The check symbols SHALL be the first 10 bits of SHA-256 over the UTF-8 bytes of `ipfs-sync/passphrase/check/v1` followed by the ASCII bytes of the 23 uppercase symbols, encoded as two base32 symbols of 5 bits each, most significant first. The canonical form SHALL be computed by one function used at setup and at unlock: remove hyphens (U+002D) and spaces (U+0020), upper-case, require exactly 25 characters each in `A-Z2-7` and a valid check, and otherwise raise the typed `passphrase-format` error before any derivation. The KDF input SHALL be the 25 uppercase symbols without separators. The passphrase SHALL be displayed in 5 groups of 5 separated by hyphens in a monospace font, with the note that letters are case-insensitive. The alphabet SHALL NOT be described as free of look-alike characters (S and 5, Z and 2, G and 6, I and L remain). The check is not secret; an interface MAY report a failed check as a probable typo without contacting any node, and doing so reveals nothing about any stored key. The check detects a mistyped symbol in the 23 body symbols with probability about 99.9% (1 minus 1 in 1,024) and a mistyped check symbol with certainty; the specification, the threat model and every interface text SHALL say "about 99.9%" or "probable typo" and SHALL NOT claim that every typo is caught. The check makes about 1 in 1,024 arbitrary 25-symbol strings valid by chance, so generation-only is a typo and accident guard and not proof that a user did not choose the text.

#### Scenario: Generated passphrase typed with separators
- **WHEN** a generated passphrase is typed in lower case without hyphens
- **THEN** the same VCK is recovered

#### Scenario: Not a generated passphrase
- **WHEN** `Correct Horse Battery Staple` or `CorrectHorseBatteryStaple` is offered
- **THEN** it is rejected with the `passphrase-format` error before any derivation

#### Scenario: Wrong length
- **WHEN** 24 or 26 valid symbols are offered
- **THEN** the input is rejected with the `passphrase-format` error before any derivation

#### Scenario: Typo in a check symbol
- **WHEN** one of the two check symbols of a generated passphrase is changed
- **THEN** the check always fails with the `passphrase-format` error and no derivation runs

#### Scenario: Typo detection rate
- **WHEN** a single random symbol change is applied at each of the 25 positions of 10,000 random generated passphrases
- **THEN** the rejection rate is at least 99.8% overall

#### Scenario: Pinned vectors
- **WHEN** the fixed vectors are checked
- **THEN** `HEZVI-DN7IB-GLQIX-B5L7V-ARDHC` is valid, and `CorrectHorseBatteryStaple` is rejected with expected check `YK` and presented check `LE`

#### Scenario: Shape and entropy
- **WHEN** a passphrase is generated
- **THEN** it has 23 random symbols drawn without modulo bias plus 2 valid check symbols, shown in 5 groups of 5, and repeated generation shows symbol frequencies consistent with uniformity for the random part

#### Scenario: Check vector
- **WHEN** the check is computed for a fixed 23-symbol input
- **THEN** it equals the recorded fixed-output vector

### Requirement: Slot creation takes only generated passphrases
Key-slot creation SHALL accept only a passphrase value produced by the generator (a branded value that the canonicalisation of typed input cannot produce), so a slot can only ever be created for a generated passphrase. Unlock SHALL accept canonicalised input (typed or pasted text that passed the canonical passphrase function).

#### Scenario: Typed text at creation
- **WHEN** slot creation is given a canonicalised value that did not come from the generator
- **THEN** it is refused before any derivation

#### Scenario: Typed text at unlock
- **WHEN** a generated passphrase is typed and canonicalised
- **THEN** unlock accepts it

### Requirement: Setup requires saving the passphrase
First-time setup SHALL show the generated passphrase once, tell the user to save it in a password manager, and require the user to enter it again before the vault is created. The generated passphrase SHALL NOT be stored by the product.

#### Scenario: Confirmation required
- **WHEN** the user has not re-entered the generated passphrase
- **THEN** the vault is not created

### Requirement: keyslots.json
`keyslots.json` SHALL be a plaintext JSON document stored in the MFS root beside `current/`. Its canonical form is: object keys sorted by UTF-16 code unit at every level, serialised as `JSON.stringify(value, null, 2)` with LF line endings and exactly one trailing newline, integers only, no duplicate keys. It SHALL contain a format version, the `vaultId` as 32 lowercase hex characters, and a list of at most 8 slots. Each slot SHALL contain its identifier (32 lowercase hex), its type, and, for a passphrase slot, the KDF algorithm and parameters with salt, the wrap nonce, the wrapped VCK and the commitment. Binary values SHALL be canonical standard base64 with padding (decoding and re-encoding SHALL reproduce the text). A reader SHALL check in this order: parse, format version, canonical form, schema. Extra fields at the document, slot, KDF and wrap levels SHALL be refused with the `malformed` error, except inside slots of an unknown type, which SHALL be skipped. If no passphrase slot remains after skipping, unlock SHALL be refused with the `no-usable-slot` error. The document SHALL contain no other key material. The slot list SHALL allow further slot types to be added later without changing existing slots.

#### Scenario: Content check
- **WHEN** `keyslots.json` is parsed after setup
- **THEN** it has exactly the documented fields, one passphrase slot, and its wrapped VCK is 48 bytes (32 plus the 16-byte tag)

#### Scenario: Unknown slot type
- **WHEN** the document holds an extra slot of an unknown type with arbitrary content
- **THEN** that slot is skipped and the passphrase slot is used

#### Scenario: Only unknown slots
- **WHEN** the document holds no passphrase slot
- **THEN** unlock is refused with the `no-usable-slot` error

#### Scenario: Unsupported version
- **WHEN** the document has a version this build does not know
- **THEN** unlock fails with the unsupported-format error before any derivation

#### Scenario: Non-canonical document
- **WHEN** the document has a duplicate key, reordered keys, non-LF line endings, a missing or doubled trailing newline, a non-integer number, or non-canonical base64
- **THEN** it is refused before any derivation

#### Scenario: Extra field
- **WHEN** a passphrase slot or its KDF or wrap object has an unexpected field
- **THEN** the document is refused with the `malformed` error

#### Scenario: Prototype keys
- **WHEN** the document contains a member named `__proto__`
- **THEN** it is treated as data or refused, and no object prototype is altered

### Requirement: Size and count caps on remote objects
Before reading a remote `keyslots.json`, the device SHALL learn its size (`files/stat` or the equivalent) and SHALL refuse a size above 16 KiB; the cap SHALL also be enforced while streaming. A document with more than 8 slots SHALL be refused. The document SHALL be parsed into objects without prototypes.

#### Scenario: Oversize document
- **WHEN** the node reports a 1 MiB `keyslots.json`
- **THEN** the device refuses it without downloading it and derives nothing

#### Scenario: Understated size
- **WHEN** the node reports 1 KiB but streams more than 16 KiB
- **THEN** the read is aborted at the cap and the document refused

#### Scenario: Too many slots
- **WHEN** the document lists 9 slots
- **THEN** it is refused

### Requirement: KDF parameter bounds and work budget
Before any derivation, the device SHALL validate the stored parameters of the (at most 2) passphrase slots it will try, all of them before the first derivation starts. It SHALL refuse memory below 19,456 KiB, iterations below 2, parallelism other than 1, a salt that is not 16 bytes, and the ceilings memory above 131,072 KiB (128 MiB) or iterations above 4, with a typed error naming the parameter. The derivation SHALL be given an explicit memory limit equal to the ceiling. A single unlock SHALL try at most 2 passphrase slots, in list order, so the worst case for one unlock is two derivations at the ceiling (2 x 131,072 KiB x 4 iterations); that worst case SHALL be reachable only after interactive confirmation. Unlock SHALL take a cost policy: by default it SHALL refuse, with a typed error, any tried slot whose parameters exceed the defaults, and the only way to allow a higher cost SHALL be a host approval callback that is called once per tried slot, after all tried slots are validated and before the first derivation. Interactive hosts SHALL supply a callback that asks the user to confirm the cost; non-interactive hosts SHALL supply none. The approval prompt SHALL come after the crypto-availability check, so a user is never asked to approve a cost that cannot be run, and the refusal error SHALL carry the offending parameters (memory, iterations, parallelism). An allocation failure during derivation SHALL be reported as a typed refusal that this device cannot afford the slot.

#### Scenario: Below the floor
- **WHEN** a slot declares memory 1,024 KiB
- **THEN** unlock is refused before Argon2id runs

#### Scenario: Above the ceiling
- **WHEN** a slot declares memory of 4 GiB, or 5 iterations
- **THEN** unlock is refused before any memory is allocated for it

#### Scenario: Default accepted
- **WHEN** a slot declares the default parameters
- **THEN** the bounds check passes

#### Scenario: Many slots
- **WHEN** three passphrase slots are present and none opens
- **THEN** at most two derivations are performed

#### Scenario: Unusual cost
- **WHEN** a slot declares 96 MiB and no approval callback is supplied
- **THEN** unlock is refused with a message naming the cost, before any derivation

#### Scenario: Approved cost
- **WHEN** the same slot is unlocked with an approval callback that returns true
- **THEN** the callback was called once for that slot before the first derivation, and unlock proceeds

#### Scenario: Prompt order
- **WHEN** `crypto.subtle` is unavailable and a slot exceeds the defaults
- **THEN** the crypto-unavailable error is raised and no approval prompt is shown

#### Scenario: Refusal carries parameters
- **WHEN** an above-default slot is refused
- **THEN** the error carries its memory, iterations and parallelism

#### Scenario: Two hostile slots
- **WHEN** two slots at the ceiling are present and no callback is supplied
- **THEN** neither is derived

### Requirement: Wrong passphrase and damaged slot are one outcome
Failure of the commitment or of the wrap authentication SHALL raise a single error meaning "wrong passphrase or damaged key slot", and unlock SHALL NOT write anything or change any state.

#### Scenario: Wrong passphrase
- **WHEN** a different passphrase is used
- **THEN** the typed error is raised, nothing is written, and no VCK is produced

### Requirement: Rewrap does not revoke
The specification SHALL state that changing the passphrase (rewrapping the slot) does not revoke the old passphrase or any old copy of the key slot: old roots stay pinned and retrievable, and an old slot copy keeps opening the same VCK. Only re-encrypting the vault under a new VCK revokes access, and this change does not provide it.

#### Scenario: Documentation
- **WHEN** the setup text and the threat-model text are read
- **THEN** both state that old passphrases and old slot copies continue to work after a rewrap

### Requirement: Local copy of the key slots, per MFS root
After a successful setup or unlock, the device SHALL keep a byte-identical copy of `keyslots.json` in the vault's `.ipfs-sync/` folder, stored per MFS root (a file name that includes a digest of the MFS root), local only and excluded from sync. The local state and the journal SHALL record the SHA-256 of that file and the `vaultId`. When the copy exists, the device SHALL unlock from it before contacting the node, SHALL compare the node's `keyslots.json` with it byte for byte, and SHALL refuse to continue on any difference, before any key derivation on node-supplied parameters. The local copy is the authority for that comparison.

#### Scenario: Wrong passphrase, no request
- **WHEN** a local copy exists and the wrong passphrase is supplied
- **THEN** the operation fails before any request is sent to the node

#### Scenario: Substituted slot file
- **WHEN** the node returns a `keyslots.json` that differs in any byte from the local copy
- **THEN** the operation stops with a vault-mismatch error, runs no derivation on the node's parameters, and writes nothing to the node

#### Scenario: Copy tied to its root
- **WHEN** the same vault directory publishes to two different MFS roots
- **THEN** each root has its own local copy and neither is compared with the other's node

### Requirement: Slots present without a manifest and without local knowledge
If the node holds `keyslots.json` but no `manifest.enc`, and the device has no local state and no local copy for that root, the device SHALL refuse before any key derivation, with a message to use a new MFS root or the explicit `--recover-slots` action. `--recover-slots` SHALL show the slot's cost first and require confirmation before deriving.

#### Scenario: Unknown slots
- **WHEN** a device with no state and no copy meets slots without a manifest
- **THEN** it refuses with no derivation, and names `--recover-slots`

#### Scenario: Recovery
- **WHEN** the user passes `--recover-slots` and confirms the shown cost
- **THEN** the device unlocks, stores the copy, and continues as the creator of an empty vault

### Requirement: Lost slots on the node
If the node's `keyslots.json` is missing while the local state says this MFS root held this vault, the operation SHALL stop and report that the node lost the key slots, without generating a new VCK. The device SHALL provide an explicit "abandon this vault" action that keeps a backup of the local copy and state, requires a typed confirmation, never modifies the node, and lets the user start a new vault in an empty MFS root.

#### Scenario: Node lost the slots
- **WHEN** the local state names the root and the node has no `keyslots.json`
- **THEN** publish stops with the lost-slots message and generates nothing

#### Scenario: Abandon
- **WHEN** the user confirms the abandon action
- **THEN** the local copy and state are moved to a backup location, the node is untouched, and the next setup can create a new vault in an empty root

### Requirement: No recovery, stated
The specification and every setup interface SHALL state that a lost passphrase, together with the loss of every copy of the key slots, makes the vault permanently unreadable, and that no recovery mechanism exists.

#### Scenario: Setup text
- **WHEN** first-time setup is presented to the user
- **THEN** the consequence text names the permanent loss of data and requires an explicit acknowledgement
